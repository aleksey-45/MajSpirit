# MajSpirit（雀灵麻将）

一个在线立直麻将平台服务端，用 Go 实现。

> **缘起**：小 X 在《雀魂麻将》中连续十把吃四后破防，认定"这个游戏一定存在着操控牌山、
> 调整和牌率的行为"，愤而卸载。作为朋友，你决定自己写一个在线立直麻将平台邀请他游玩，
> 让他对比判断——这个平台就叫《雀灵麻将》（MajSpirit）。
>
> 本仓库是这份实习任务书的实现。

## 快速开始

**环境要求**：Go 1.22 或更高（本项目在 Go 1.27 上开发）。

```bash
# 编译全部包
go build ./...

# 运行全部测试（-p 1 必须有，理由见下）
go test -p 1 ./...

# 查看可用命令
make help
```

> **`-p 1` 不是可选的。** `internal/store` 的用例会 `DROP SCHEMA`，而
> `cmd/server` 的集成测试在同一个库上跑迁移；两个包并行时，前者会插在后者的
> 两条迁移中间（实测报「关系 users 不存在」）。`make test` / `make test-db`
> 已经带上了这个开关。这是测试夹具的性质，生产不受影响。

其他常用命令：`make vet`（静态检查）、`make build`（产出二进制）、`make lint`（staticcheck）。

> **调试客户端**：起服务端后打开 <http://127.0.0.1:8080/>（`bash scripts/serve.sh --bg`）。
> 它连的是同一个源上的 `/ws`，能填票发 `auth`、看到每一条事件与**关闭码**。
> 必须由服务端 serve，不能双击 HTML 打开 —— `file://` 会发 `Origin: null`，被握手拒掉。

## 项目结构

```
MajSpirit/
├── cmd/
│   └── server/                   程序入口：装配依赖，启动 HTTP + WebSocket + 调试页
│
├── internal/
│   ├── mahjong/                  ★ 纯规则包，零 IO 依赖，全靠单测保证
│   ├── auth/                     JWT 签发校验、bcrypt 密码哈希
│   ├── user/                     用户用例：注册 / 登入 / 登出
│   ├── store/                    数据访问：用户表、牌局记录
│   ├── room/                     房间与对局调度（actor 模型）
│   ├── ws/                       WebSocket 传输层与协议编解码
│   └── api/                      HTTP 路由、中间件与 handler
│
├── migrations/                   建表 SQL
├── web/                          §3.3 调试客户端（embed 进二进制，由 Go 在 `GET /{$}` 上 serve）
├── Dockerfile                    多阶段构建，产出静态二进制
├── docker-compose.yml            app + PostgreSQL
└── Makefile
```

每个包的职责边界与**禁止事项**写在对应的 `doc.go` 里，动手前先读它。

### 依赖方向

单向、无环：

```
cmd  →  api / ws  →  room  →  mahjong
                       ↓
              user / auth / store
```

`mahjong` 不依赖任何其他包，也不依赖标准库以外的任何东西。
`web` 只被 `cmd/server` 引用，是调试页的静态资源，不参与上面这条链。

## 架构要点

### 1. 规则是纯函数，可被完整测试

`internal/mahjong` 只包含无 IO 的纯逻辑：牌的表示、牌山、手牌、和牌判定。
所有函数要么是纯函数，要么只操作自身状态，因此可以被单元测试完全覆盖。

这是整个项目最容易写出隐蔽 bug 的地方（和牌判定的回溯、顺子跨花色、
字牌不能组顺子等等），所以它被隔离成最深的模块：**接口小、实现厚、测试密**。

上层任何地方都不应该复制规则，也不应该把网络或数据库概念漏进来。

### 2. 房间用 actor 模型，不用锁

每个房间由一个独立的 goroutine 独占其全部状态，外部通过 channel 投递指令，
由该 goroutine 串行处理。

这从根本上消除了"四个玩家并发操作同一局牌"的竞态——状态只在一处被读写，
不需要给共享状态加锁，也就不存在忘记加锁或加锁顺序错误这类问题。

### 3. 传输与逻辑分离

`internal/ws` 只管连接生命周期与协议编解码，不含任何游戏规则；
`internal/room` 通过接口回调对外发消息，不直接依赖 WebSocket。

代价是多一层接口，好处是**对局逻辑可以完全脱离网络测试**。

## 规则层的设计约定

以下表示法在动手实现 `internal/mahjong` 之前已经定好，测试用例、日志与数据库
共用同一套表示，避免各处自行编码。

### 牌的编码

34 种牌编码为 `0..33`：

| 范围    | 含义                 |
| ------- | -------------------- |
| `0-8`   | 一万 ～ 九万         |
| `9-17`  | 一条 ～ 九条         |
| `18-26` | 一饼 ～ 九饼         |
| `27-33` | 东 南 西 北 白 发 中 |

牌的类型表示**种类**，不区分同类牌的四张副本——一副牌由 136 个该类型的值组成，
重复出现即代表副本。

### 紧凑记法

`m` / `s` / `p` / `z` 分别表示万 / 条 / 饼 / 字牌，字母前的数字是点数：

```
"123m"              一万 二万 三万
"11z"               东 东
"123m456s789p11z"   共 11 张
```

字牌的 `1z` ～ `7z` 依次为东、南、西、北、白、发、中。

**赤宝牌写作 `0m` / `0s` / `0p`**，即用数字 `0` 表示该花色的红 5，这是网络麻将的通行写法：

```
"055m"   红五万、五万、五万
```

注意 `0m` 与 `5m` 的**种类相同**，差别只在赤属性。实现上赤五用**额外的编号**
34/35/36 表示（`AkaMan5`/`AkaSou5`/`AkaPin5`），`NumTileKinds` 仍是 34——
赤属性是叠加在种类之上的独立维度：和牌判定、役种、符数都只看种类（先过 `Tile.Kind()`），
只有数赤宝牌时才需要区分。

为什么不做成"解析时归一成普通五"：那样牌山指纹就**绑不住赤五的位置**，
服务器可以在公布承诺值之后再决定赤牌发给谁。

解析与格式化必须互为逆运算，并有对应测试。

### 和牌型

完整规则下合法的和牌型有三种：

| 和牌型 | 结构 | 说明 |
|---|---|---|
| 标准型 | 4 个面子 + 1 个雀头 | 面子是顺子（3 张同花色连续数字牌）或刻子（3 张完全一样）|
| 七对子 | 7 个对子 | 门清限定，固定 25 符 |
| 国士无双 | 13 种幺九牌各一张 + 其中一张成对 | 役满 |

同一种牌型可能有多种拆法（例如 `111222333m` 既可拆成三个刻子也可拆成三个顺子）。
不同拆法会影响役种成立与符数，因此拆解不能只返回"任意一种"——
需要能枚举候选拆法，供役种判定择优。

### 役种与算点

**没有役就不能和牌**，哪怕牌型合法。这是立直麻将区别于简化规则最本质的一条。

役种一览、符数计算、基本点与满贯封顶、支付规则、点数速查表、
以及 **M-League 与通用日麻的差异清单**（双倍役满 / 累计役满 / 途中流局 / 包 / 連風牌符数……），
全部写在 [`docs/规则集.md`](docs/规则集.md) 里，
那份文档是规则与算点的**唯一权威依据**，每条结论都标注了出处
（【M】M-League 原文 /【連】连盟 /【慣】社区惯例）。
本 README 不重复其内容，避免两处表述漂移。

## 开发规范

### 提交信息

采用约定式提交（Conventional Commits）：

```
<type>(<scope>): <描述>

feat     新功能
fix      修 bug
refactor 重构（不改变外部行为）
docs     文档
test     测试
chore    构建、依赖、杂务
```

示例：

```
feat(mahjong): 实现和牌判定与牌型拆解
fix(wall): 发牌时校验余牌是否足够
docs: 补充规则层与房间层的依赖说明
```

### 开发日志

任务书 §1 要求记录开发过程：

| 文件 | 内容 | 风格 |
|---|---|---|
| [`docs/开发日志.md`](docs/开发日志.md) | 每天真实做了什么、当时的取舍与犹豫 | 手写日记 |

> **`docs/local/devlog/`（按日期分文件的结构化纪要）只在本地保留，不进仓库**——
> 它和上面那份是同一段过程的两种记法，公开一份就够了。见 `.gitignore` 的「过程文档」一节。

### 代码风格

- 提交前跑 `make vet` 与 `make test`
- 导出的标识符必须有文档注释，注释说明**为什么**而非复述**做了什么**
- 单元测试用表驱动（table-driven）风格

仓库根目录的 `MajSpirit.pdf` 是任务书原件。

需要注意的是，该 PDF 由 Typora 导出，**内嵌字体的数字缺少有效的 Unicode 映射**，
