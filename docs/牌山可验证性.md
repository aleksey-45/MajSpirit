# 牌山可验证性

本文档定义 MajSpirit 如何让**牌山可以被玩家独立验证**。

> **与任务书的关系**：任务书 §0 是一个**情景引入**——小 X 连吃四把就认定《雀魂麻将》
> "操控牌山"。那是角色的情绪化调侃，不是待证的事实；任务书自己的措辞也是
> 「让他对比判断一下……**是否存在**」。
>
> 所以这个功能要解决的不是"证明谁作弊"，而是：**让这个问题第一次变得可回答。**
> 数据还是那些数据，但性质变了——从「服务器说的」变成「可被独立核验的」。
>
> ⚠️ **也别把它当成独门绝技**：雀魂与天鳳本来就有同类机制（天鳳甚至公开牌山生成
> 伪代码与全部对局日志），Maru-Jan 也在 2025 年底发布了「无牌操作证明」。
> **本项目做的是对齐行业已有标准，不是发明它。** 详见 §3.6。

---

## 1. 问题是什么

牌山由服务器生成。玩家凭什么相信它没被动过手脚？

潜在的三类作弊：

| 作弊方式 | 具体做法 |
|---|---|
| **事前挑选** | 生成很多副牌山，挑一副对某位玩家（或对营收）有利的 |
| **事中调换** | 玩家快和牌了，把关键牌换掉 |
| **事后抵赖** | 被质疑时声称"就是这么发的"，没有可核对的凭证 |

单靠"我们不会作弊"的承诺解决不了任何问题。需要的是**密码学意义上的约束**。

---

## 2. 两个层次

| 层次 | 做到什么 | 成本 |
|---|---|---|
| **层次 1：可复现** | 给定种子必然产出同一副牌山，可被重放 | 低，必做 |
| **层次 2：可验证** | 服务器**事前**无法挑选、**事后**无法抵赖 | 中，雀魂 / 天鳳 / Maru-Jan 已各自实现 |

层次 1 是层次 2 的前提。没有确定性洗牌，一切验证都无从谈起。

## 3. commit-reveal 协议

### 3.1 流程

```
① 开赛前   服务器生成 serverSeed（密码学随机，32 字节）
           公布  commitment = SHA256(域分隔串 ‖ gameID ‖ serverSeed)
                   ↑ 此时 serverSeed 本身保密

② 开赛前   四位玩家各自提交一个 clientSeed（明文，按座位号固定顺序）

③ 每小局   派生  finalSeed = SHA256(域分隔串 ‖ gameID ‖ roundIndex
                                    ‖ serverSeed ‖ clientSeed₀ ‖ … ‖ clientSeed₃)
           牌山 = NewWallFromSeed(finalSeed)

④ 牌局结束后  服务器公布 serverSeed

⑤ 任何人   验证两件事：
              a) SHA256(域分隔串 ‖ gameID ‖ serverSeed) == ①里公布的 commitment
              b) 用 ③ 的公式重算，得到的 136 张与存档里的牌山逐张一致
```

#### 字节表 ★ 这一节就是契约

哈希输入是一串**没有结构**的字节。所以每个字段的宽度必须写死，否则第三方照文档
实现会算出不同的哈希——那不是"实现差异"，而是**误判服务器作弊**。

| 字段 | 宽度 | 编码 |
| --- | :--: | --- |
| 域分隔串 | **17** | ASCII，具体值见 §3.3 |
| `gameID` | **8** | int64，**big-endian** |
| `roundIndex` | **8** | int64，**big-endian** |
| `serverSeed` | 32 | 原样 |
| `clientSeed₀ … clientSeed₃` | 32 × 4 | 按**座位号顺序**，原样 |

于是两个长度也是契约的一部分：

```
承诺值   = SHA256( 域分隔串 ‖ gameID ‖ serverSeed )                        共 57 字节
最终种子 = SHA256( 域分隔串 ‖ gameID ‖ roundIndex ‖ serverSeed ‖ 四个 clientSeed )
                                                                           共 193 字节
```

**为什么 `roundIndex` 也要 8 字节，不用 1 字节**：输入里没有"哪个字节属于哪个字段"的
标记，而**定宽**是唯一不需要额外记号就能切开的方式。另外写成 1 字节的话 `0` 和 `256`
会派生出**完全相同**的种子——同一承诺下两小局的牌山一样，验证直接失效。

**为什么这里不需要分隔符**：所有字段都定宽，切法唯一。**将来若加入变长字段**
（比如玩家名），就必须改成"长度前缀 + 内容"——否则 `("ab","c")` 与 `("a","bc")`
会拼出同一串字节，两个语义不同的输入共用一个摘要。

> 实现见 `internal/mahjong/verify.go`。测试 `verify_test.go` 里的期望值是**照本节
> 独立重算**的，不是调实现比对实现——否则"外面多套一层哈希"这种错它一个都抓不到。

### 3.2 为什么这样就能防住

两条性质各自挡住一种作弊：

| 机制 | 挡住什么 | 依赖的数学性质 |
|---|---|---|
| **先公布哈希** | 事后改不了种子 | SHA-256 的抗碰撞性 |
| **混入玩家种子** | 事前挑不了种子 | 服务器必须先承诺，而玩家种子它事先不知道 |

**缺任何一条都有漏洞：**

- 只公布哈希、不混玩家种子 → 服务器可以生成一万个种子，挑一个顺眼的再公布它的哈希。**事后**改不了，但**事前**随便挑。
- 只混玩家种子、不先承诺 → 服务器可以等收到玩家种子后，再换掉自己的种子，反复试到满意为止。

两者结合才闭合。

### 3.3 域分隔（domain separation）

哈希输入的第一段是固定的**域分隔串**。本项目取：

```
"majspirit/wall/v1"        （ASCII，17 字节）
```

代码里的常量名是 `wallDomain`（`internal/mahjong/verify.go`）。

作用有两条：

1. **跨协议隔离** —— 把本协议的哈希和程序里其他地方的哈希隔开。没有它，
   一个精心构造的输入可能让两处哈希撞上（**跨协议攻击**）：同一个摘要同时
   属于两个语义不同的东西，就能互相冒充。
2. **版本位** —— 将来协议升级时把 `v1` 改成 `v2`，前缀一变，新旧输入继续不相交，
   历史记录不会和现在的记录混淆。

**⚠️ 改这个串等于改协议版本。** 它出现在 §3.1 字节表的第一行，任何改动都必须
同步本节与那一节——否则第三方照文档复算会得到不同结果，进而**误判服务器作弊**。

**这是个很小的习惯，但省掉它以后会很难受。**

### 3.4 玩家种子不必保密

`clientSeed` 用明文提交即可。玩家无法"磨"自己的种子来求一个好牌山——因为派生需要
`serverSeed`，而他只见过它的哈希。

最后一个提交种子的玩家也不行：同样缺 `serverSeed`。

### 3.5 「完整性」与「无偏性」是两件事 ★

这套协议证明的是**完整性**（integrity）：

> 牌山在开局那一刻就定死了，之后没有被换过。

它**不**证明**无偏性**（unbiasedness）：

> 洗牌算法本身不偏向任何人。

| | 证明什么 | 靠什么 | 谁做到了 |
| --- | --- | --- | --- |
| **完整性** | 开局后牌山没被改动 | 承诺 + 哈希 | 雀魂、天鳳、Maru-Jan、本项目 |
| **无偏性** | 生成器不偏爱谁 | 对海量牌山做卡方 / 游程检验 | **公开可查的严格结论：没有** |

**为什么这个区分要紧**：你完全可以对一个**有偏的生成器**做完美的 commit-reveal。
承诺锁住的是"这副牌山是什么"，锁不住"生成器偏向谁"。哈希再漂亮，也证明不了
`Shuffle` 没有系统性地让某类牌更容易落到某个座位。

**而这恰好是一条公开可检验、却没人做过的路**——数据是公开的（雀魂牌谱带牌山代码，
天鳳牌谱可复算牌山），社区也已经有数据管道，但没有人发布过严格的检验结论。

所以对"牌山有没有被操控"这个问题，行业目前的答案是：

> **「没被事后改动」已经能证明；「生成时就没偏」还没人证过。**

§13 记了这条路该怎么走。

### 3.6 行业现状：这不是独门绝技

| 平台 | 做法 | 公开程度 |
| --- | --- | --- |
| **天鳳** | [专页《牌山乱数》](https://cdn.tenhou.net/stat/rand/) 公开牌山生成**伪代码**、SHA512 哈希列表、登录前即定的种子；[全部对局日志](https://tenhou.net/sc/raw/) 公开 | **最彻底**，是标杆 |
| **雀魂** | 局中可查看本局牌山 SHA-256；赛后用「牌山代码 + 盐」重算比对（2024-02-28 起加盐） | 机制在游戏内，官网未查到网页版说明 |
| **Maru-Jan** | 局中显示 SHA-1，赛后公布牌山数据供自验 | [官方公告 2025-12-18](https://www.signaltrt.com/press/20251218.php) |

> ⚠️ **出处等级不一致，必须标出来**：天鳳那条是一手（官方页面）；**雀魂那条我只拿到
> 二手转录**（原页面是游戏内的文本），官网用户协议里没有"随机数 / 牌山"相关条款。
> 结论方向可信，但**出处等级低于天鳳**。不标这一点，就犯了本文档在防的同一个错。

**对本项目的意义**：这是一个**有参照实现**的功能，不是凭空发明。天鳳的页面就是标杆，
可以逐条对照还差什么。

## 4. 随机源与种子

### 4.1 用 `math/rand/v2`，种子是 `[32]byte`

| 包 | 构造 | seed 类型 |
|---|---|---|
| `math/rand`（v1） | `rand.NewSource(seed int64)` | `int64` |
| `math/rand/v2` | `rand.NewPCG(seed1, seed2 uint64)` | 两个 `uint64` |
| **`math/rand/v2`** | **`rand.NewChaCha8(seed [32]byte)`** | **`[32]byte`** |

**本项目选 ChaCha8，两个理由：**

1. **32 字节种子正好是一个哈希输出的大小**，和上面的派生公式天然对齐，不需要额外的
   类型转换规则。
2. **ChaCha8 是一个有公开规范的算法**。PCG 有多个变体参数，而 ChaCha8 的密钥流由
   算法本身完全确定——这对"三年后还能验证"是必要的。

### 4.2 绝不能用全局随机源

`math/rand/v2` **没有** `rand.Seed()`（v1 的已废弃并移除）。这不是疏漏，是设计——
给全局源播种会导致库之间互相覆盖对方的种子。

推论：**要可复现，就必须注入自己的 `*rand.Rand`**。

```go
rand.Shuffle(...)   // ✗ 全局源，无法复现
r.Shuffle(...)      // ✓ r 是调用方注入的
```

## 5. 洗牌必须自己写

### 5.1 问题

标准库的 `rand.Shuffle` 是 Fisher-Yates，但**从随机字节流到"交换哪两个下标"的映射
属于实现细节**（怎么取模、怎么做拒绝采样）。Go 不承诺这部分跨版本不变。

对"三年后别人还要验证这局牌"来说，这是个真实的隐患。

### 5.2 做法：把算法钉死

自己写 Fisher-Yates，每一处都确定下来：

```go
// Shuffle 用 r 的确定性字节流就地重排 tiles。
// 算法固定为 Fisher-Yates 的降序形式，见 docs/牌山可验证性.md。
func Shuffle(tiles []Tile, r *rand.Rand) {
    for i := len(tiles) - 1; i > 0; i-- {
        j := int(r.Uint64() % uint64(i+1))
        tiles[i], tiles[j] = tiles[j], tiles[i]
    }
}
```

`r.Uint64()` 从 ChaCha8 的密钥流直接读 8 字节，语义明确。取模会引入极小的分布偏差
（`2^64 mod m` 那点余数），**但该偏差的上界是可以算出来的，所以不必用"可以接受"糊过去**：

```
m 最大 136（剩两张时要选 136 个位置）
偏差上界 = (m-1)/2^64 = 7.318e-18

用卡方检验检出这个量级需要 ~1e34 次抽取
一个玩家一年打 1000 局 = 136,000 次抽取
→ 需要约 1.4e29 个玩家打一年
```

**所以这不是"可以接受"，是"可证明无法检出"。** 两个说法差得很远：前者是让步，
后者是结论。

（想彻底消掉也有标准做法——拒绝采样，即丢掉 `2^64 mod m` 那段余数区间。代价是
每次抽取有极小概率重抽。本项目不做，因为上界已经低到没有意义。）

**有偏差不可怕，不量化才可怕**——这正是"牌山操控"这类指控能长期存活的机制（见 §3.5）。

### 5.3 兜底：牌山指纹回归测试

即使算法钉死了，也挡不住运行时的意外变化。加一条测试把结果固化：

```go
func TestWallFingerprint(t *testing.T) {
    w := NewWallFromSeed(testSeed)
    got := sha256.Sum256(w.Bytes())
    if got != wantFingerprint {   // 常量写死
        t.Fatalf("洗牌结果变了，可能由 Go 版本升级导致，请核对后更新常量")
    }
}
```

**它把"跨版本稳定"从一个假设，变成了一个会被测试发现的事实。**

## 6. 序列化与哈希

### 6.1 ⚠️ `FormatTiles` 不能用来哈希牌山

`FormatTiles` 的语义是「**牌组**」，输出按花色分组、组内排序——它丢掉了顺序：

```
[一万, 二万, 三万, …]  和  [三万, 二万, 一万, …]
FormatTiles 两者都输出 "123m…"
```

而**牌山的顺序就是全部信息**。用 `FormatTiles` 做哈希输入，等于让所有同花色组合的
牌山共用同一个指纹——验证彻底失效。

这条要写进 `FormatTiles` 的文档注释里，否则以后一定有人踩。

### 6.2 用原始字节

`Tile` 本身就是 `uint8`，136 张牌就是一个 136 字节的切片。直接哈希它：

```go
// Bytes 返回 136 张牌的原始摸牌顺序。哈希牌山用这个，不要用 FormatTiles。
func (w *Wall) Bytes() []byte
```

简单、紧凑、无歧义。

### 6.3 可读的存档是另一回事

**哈希输入不需要可读，但记录需要可读。**

`game_walls.tiles` 那一列继续用紧凑记法存，但要**按摸牌顺序**逐张写（不是分组），
例如 `"1m5p3s2z…"` 共 136 组。它比字节形式长约三倍，换来的是人工核对时能直接看懂。

两者用途不同，不要合并。

## 7. 接口形状

```go
// ── wall.go ──────────────────────────────────────────────

// NewWallFromSeed 用确定性种子构造牌山。
// 同一个种子必须永远产出同一副牌山——这是全部验证的前提。
func NewWallFromSeed(seed [32]byte) *Wall

// NewWall 用注入的随机源构造牌山。
// 供测试与不需要留存的场合使用；需要存档的牌局一律走 NewWallFromSeed。
func NewWall(r *rand.Rand) *Wall

// Bytes 返回 136 张牌的原始摸牌顺序，供哈希使用。
func (w *Wall) Bytes() []byte

// Sequence 返回按摸牌顺序写成的紧凑记法，供人工核对与入库。
func (w *Wall) Sequence() string

// ── verify.go ────────────────────────────────────────────

// Commit 返回承诺值。开赛前公布它，牌局结束后再公布 serverSeed。
func Commit(gameID int64, serverSeed [32]byte) [32]byte

// DeriveSeed 把服务器种子与各玩家的种子按座位顺序混合成最终种子。
// 顺序必须固定，否则无法复现。
func DeriveSeed(gameID int64, roundIndex int, serverSeed [32]byte,
    clientSeeds [4][32]byte) [32]byte

// WallHash 返回牌山指纹，与数据库里记录的值比对即可核验整局。
func WallHash(w *Wall) [32]byte
```

**`NewWall` 与 `NewWallFromSeed` 并存**是有意的：前者服务测试（传固定种子的
`*rand.Rand` 就够），后者服务生产（种子要入库、要公布）。不要用 `NewWall` 去发真牌局。

## 8. 数据落地

`migrations/0001_init.sql` 的 `game_walls` 表需要补充：

| 列 | 类型 | 说明 |
|---|---|---|
| `tiles` | `TEXT` | 按摸牌顺序的紧凑记法，136 组 |
| `wall_hash` | `BYTEA` | 牌山指纹，核验时先比它 |
| `server_seed` | `BYTEA` | 牌局结束后公布 |
| `commitment` | `BYTEA` | 开赛前就记录，用于事后比对 |
| `client_seeds` | `BYTEA[]` | 四位玩家按座位顺序提交的种子 |
| `go_version` | `TEXT` | 洗牌实现依赖的运行时版本 |

`go_version` 不是洁癖，是第 5 节的兜底：万一哪天 Go 真的改了 shuffle 行为，
至少知道该用哪个版本去验证历史牌局。

**承诺值必须在开赛前入库**，不能等牌局结束一起写——那等于没有承诺。

## 9. 玩家视角的验证流程

这是整套机制的价值所在，也是验收展示时最有说服力的一段：

```
1. 从 /api/games/{id} 取到：
     commitment      （开赛前就公布过的）
     server_seed     （牌局结束后公布的）
     client_seeds    （四位玩家的）
     tiles / wall_hash

2. 自己算一遍 SHA256(域分隔串 ‖ gameID ‖ server_seed)
   与 commitment 比对        → 证明种子没被事后替换

3. 自己算一遍 finalSeed = SHA256(域分隔串 ‖ gameID ‖ roundIndex
                                 ‖ server_seed ‖ client_seeds…)
   （逐字段宽度照 §3.1 的字节表，一个字节都不能自己发挥）

4. 用 finalSeed 自己重放洗牌，得到 136 张
   与 tiles 逐张比对          → 证明牌山确实是这个种子生成的

5. 两边都通过 → 这一局的牌山没有被操控
```

**第 3 步是整套机制最脆的地方**：玩家必须能**逐字节**复现服务端拼的输入。
差一个字节（多套一层哈希、少写域分隔串、`roundIndex` 用 1 字节）都会算出
不同的 `finalSeed`，然后牌山对不上——**而玩家没有理由认为错的是自己**。

所以 §3.1 的字节表不是文档装饰，它就是这份契约的正文。

**服务端应当把第 2~4 步做成一个 `/api/games/{id}/verify` 接口**，让玩家不用自己写代码。
但**同时也要把原始数据暴露出来**——"我们提供了一键验证"和"你可以自己验证"是两回事，
后者才是真正的可信。

## 10. 局限（诚实说明）

这套机制解决的是**牌山生成的可信度**，不是万能药。以下问题它**管不了**：

| 局限 | 说明 |
|---|---|
| **服务器仍然能看到所有人的手牌** | 承诺只约束"牌山是什么"，不约束"服务器拿它做了什么" |
| **无法防止服务器给同伙报牌** | 那需要另一种机制（如不公开手牌给服务端，或可信执行环境） |
| **不能证明发牌顺序没被篡改** | 协议保证的是"给定种子产出这副牌"，摸牌顺序的正确性由房间逻辑保证 |
| **玩家种子需及时收集** | 若允许牌局中途提交，就失去了"服务器事先不知道"的性质 |
| **模偏差** | 第 5.2 节的取模方式偏差上界 `7.318e-18`——**可证明无法检出**，不是"可以接受" |
| **只证完整性，不证无偏性** ★ | 承诺锁住"牌山是什么"，锁不住"生成器偏向谁"。见 §3.5 |

**把这些写清楚，比假装方案无懈可击更专业。** 验收时被问到"那服务器还是能看到牌啊"，
能立刻答出"对，那属于另一类问题，需要 X 机制"的人，和支支吾吾的人是完全不同的。

## 11. 测试要点

**期望值一律照 §3.1 的字节表独立重算**，不调实现去比对实现——否则"外面多套一层哈希"
「少写域分隔串」「`roundIndex` 截成 1 字节」这三种错，一个都抓不到。

| 测试 | 断言 | 实现于 |
| --- | --- | --- |
| **字节表** | 承诺输入 57 字节、派生输入 193 字节、域分隔串 17 字节 | `verify_test.go` |
| **等于文档公式** ★ | 实现结果 == 照字节表独立算出的结果 | `verify_test.go` |
| **确定性** | 同种子两次构造，136 张逐张相同 | `wall_test.go` |
| **不变量** | 洗牌是排列（前后多重集一致） | `wall_test.go` |
| **指纹回归** | 固定种子的 SHA-256 等于写死的常量 | `wall_test.go` |
| **承诺自洽** | `Commit` 两次调用结果相同；改一个字节（含 `gameID`）结果就变 | `verify_test.go` |
| **派生顺序敏感** | 交换任意两人的 clientSeed、或整体移位，结果必须不同 | `verify_test.go` |
| **派生绑定上下文** | 改 `gameID` / `roundIndex` / `serverSeed` / 任一 clientSeed 字节，结果都不同 | `verify_test.go` |
| **`roundIndex` 不截断** | 0 / 256 / 512 必须给出**三个不同的**种子 | `verify_test.go` |
| **重放可复现** ★ | 用记录里的种子重放，得到与 `tiles` 逐张一致的牌山 | `verify_test.go` |
| **`WallHash` 用原始字节** | 同花色组合相同但顺序不同的牌山，指纹必须不同 | `verify_test.go` |
| **`Bytes` 与 `Sequence` 一致** | 两条路径还原出同一个牌山 | `wall_test.go` |

打 ★ 的两条是核心：**「等于文档公式」保证服务端没有偏离契约，「重放可复现」模拟的
就是玩家第 9 节的第 4 步。**

## 13. 一个还没人做的方向：检验无偏性

§3.5 说清楚了：**完整性已经有人证，无偏性没有。**

这一节记下这条路——它可能是这个项目里**唯一真正原创**的部分。

### 数据是现成的

| 来源 | 拿到什么 |
| --- | --- |
| 雀魂牌谱 | 牌山代码（含盐），可复算哈希 |
| 天鳳牌谱 | 可复算牌山，且全量日志公开 |

### 要做的检验

- **牌山内位置分布**：每种牌落在 136 个位置上的分布是否均匀（卡方检验）
- **起手牌分布**：每个座位的 13 张是否同分布（卡方 / KS）
- **游程检验**：连续同花色 / 同点数的长度是否符合随机预期
- **和牌率 / 放铳率**：与已发表的描述统计基线比对（如とつげき東北《新 科学する麻雀》）

### 难点不在算法，在统计纪律

1. **多重比较必须校正。** 你会同时检验几十个假设，不校正的话总会有几个"显著"——
   这就是**把方差当规律**，也正是"牌山操控"这类指控能长期存活的机制
2. **样本量要事先算。** 想检出多小的偏差，就需要多大的 N——反过来也能算"检出不了多小"
3. **检验方案要事先定死**，不能看着数据挑假设。否则就是先开枪再画靶子

### 期望的结果

诚实地讲：**最可能的结果是"查不出显著异常"。**

**但那也是结论**，而且是第一个由**公开数据支撑**的结论——比"很多人都在说"
和"我相信它没作弊"都强得多。

> 这条如果做成，是可以拿去讲的：
> **一个原本只能靠感觉的问题，变成了能算出答案的问题。**
