## 0. 先说清楚这个包的位置

`mahjong` 是**纯规则包：零 IO、零网络、零数据库**。它不认识 HTTP、WebSocket、数据库，甚至不认识"房间"。

分层（箭头是依赖方向）：

```
cmd → api / ws → room → mahjong
```

所以：

- **`mahjong` 里的函数都是纯函数**，或者只操作自己持有的状态（`Wall` / `Hand`）。同输入必同输出——这是整个包可被 100% 单测覆盖的前提。
- **上层的逻辑不许漏进来**。比如"庄家的第 14 张什么时候摸"是 `room` 的事，不是 `mahjong` 的事。
- **反过来，规则也不许抄到上层去**。`room` 判定能不能和牌必须调 `mahjong.CanWin`，不能自己写一遍。

### 一句话概括数据流

```
字符串 "123m456s789p11z"
   │ ParseTiles
   ▼
[]Tile ──── NewWallFromSeed ──→ Wall ── Deal ──→ 四家的 []Tile
   │                                                │
   │                                                ▼
   │                                          Hand（可变容器）
   │                                                │ Counts()
   │                                                ▼
   │                                          Counts（34 长度直方图）
   │                                                │ Decompose
   │                                                ▼
   │                                  []Decomposition（全部候选拆法）
   │                                                │ DetectYaku / CalcFu
   │                                                ▼
   │                                    []YakuHit / int(fu)
   │                                                │ CountDora（第 ⑥ 步，加宝牌翻数）
   │                                                │ CalcScore
   │                                                ▼
   │                                          [4]int（各家收支，按座位索引）
   │
   └──── FormatTiles ───→ 字符串（回到原点）
```

**注意中间那条分叉**：`Tile` 切片是**面向"一张张牌"**的表示，适合增删和传输；`Counts` 是**面向"每种几张"**的表示，适合规则判定。整个包的核心设计就是在这两种表示之间来回翻译。

## 1. `tile.go` —— 牌本身

### 类型与常量

#### `type Suit uint8` ✅

花色。只有 4 个值：

| 常量 | 值 | 含义 | 对应记法字母 |
| --- | --- | --- | --- |
| `SuitMan` | 0 | 万 | `m` |
| `SuitSou` | 1 | 索 | `s` |
| `SuitPin` | 2 | 筒 | `p` |
| `SuitHonor` | 3 | 字牌 | `z` |

**为什么单独一个类型而不是裸 `int`**：`NewTile` 要拒绝非法花色。用 `int` 的话 `NewTile(9, 1)` 编译期看不出来。

#### `type Tile uint8` ✅

**一种牌**，取值 `0..33`。注意是**种类**，不是物理牌——`Tile` 不知道"这是四张一万里的第几张"。

| 区段 | 含义 |
| --- | --- |
| 0–8 | 一万 … 九万 |
| 9–17 | 一索 … 九索 |
| 18–26 | 一筒 … 九筒 |
| 27–30 | 东 南 西 北 |
| 31–33 | 白 发 中 |
| **34–36** | **赤五万 / 赤五索 / 赤五筒** |

**为什么用 `uint8`**：能直接当 `[34]int` 的下标用（见 `Counts`），零转换成本。

**赤五牌用额外的编号**，`NumTileKinds` 仍是 34（它是**种类**数，也是 `Counts` 的长度）。
赤属性是叠加在种类之上的独立维度：`Kind()` 把 34/35/36 归一到 4/13/22，
**规则判定一律走 `Kind()`**，只有 `CountAka` 直接看 `IsAka()`。

⚠️ **不要因为 `Tile` 现在有 37 个合法写码，就把 `Counts` 改成 `[37]int`。**
那样赤五万会落进一个和普通五万不同的桶：手里有赤五万就拆不出顺子，
而且「4 张普通五 + 1 张赤五」会被放过去。归一化必须在 `CountTiles` / `Hand.Counts`
里做，`Counts` 的长度不能变。

#### 数量常量 ✅

| 常量 | 值 | 含义 |
| --- | --- | --- |
| `NumTileKinds` | 34 | 牌的**种类**数 |
| `NumTiles` | 136 | 一副牌的**张数**（= 34 × 4） |
| `HandSize` | 13 | 配牌张数 |
| `WinningHandSize` | 14 | 和牌时手牌张数 |
| `numNumberKinds` | 27 | 数牌种类数（**未导出**） |
| `numHonorKinds` | 7 | 字牌种类数（**未导出**） |
| `numCopies` | 4 | 每种牌的张数（**未导出**） |

**`NumTileKinds` 与 `NumTiles` 的区别是最容易搞混的一对**：前者是"几种"，后者是"几张"。`[NumTileKinds]int` 是直方图，`make([]Tile, NumTiles)` 是一整副牌。

**前三个导出、后三个不导出的理由**：上层需要知道"34 种""136 张""13 张""14 张"这些**业务数字**；但 `27`、`7`、`4` 是**实现细节**——哪天要支持三麻（去掉二万到八万）或者改每种张数，导出它们就等于对外承诺了。

#### 字牌点数常量 ✅

`HonorEast`=1 … `HonorNorth`=4，`HonorWhite`=5，`HonorGreen`=6，`HonorRed`=7。

**为什么风牌和三元牌连号**：因为 `Rank()` 对字牌也返回 1–7，而 `String()` 用 `honorNames[t.Rank()-1]` 直接索引。如果给它们各自编 1–4 和 1–3，`Rank()` 就要分支判断了。

**为什么是 `const` 而不是 `Suit` 那样的类型化常量**：它们只用于和 `Rank()` 比较，不构成独立概念。

### 函数

#### `func (t Tile) Valid() bool` ✅

**做什么** —— 报告 `t` 是否落在 `0..36` 内。就一句 `t < NumTileCodes`。

**为什么它必须是最底层的** —— 它的实现**不能调用任何其他方法**。这条是踩过坑写下来的：早期版本 `Valid()` 调了 `Suit()`、`Suit()` 又调 `Valid()`，无限互递归，`go test` 直接 `fatal error: stack overflow`。

**谁用** —— `IsNumber()`、`IsHonor()`、`String()`、`FormatTiles()` 全部以它开头。所有"接受任意 `Tile` 参数"的函数都该用它挡一下。

⚠️ **它是纯范围的，不是纯语义的**。`Tile(27)` 是合法的（东），`Tile(34)` 也是合法的（赤五万），但 `Tile(37)` 不是。它**不检查**这张牌在一副牌里是否存在、是否超过 4 张——那是 `CountTiles` 的责任。

⚠️ **`NumTileCodes`（37）与 `NumTileKinds`（34）是两个不同的数**，混用会很痛：前者是合法写码数，只给 `Valid` 用；后者是**种类**数，是 `Counts` 的数组长度。`Counts` 一旦按 37 建，赤五万就会分到独立的桶里——见 §1 开头的警告。

#### `func (t Tile) IsAka() bool` ✅

**做什么** —— 报告 `t` 是不是赤宝牌（34/35/36）。越界值一律 `false`。

#### `func (t Tile) Kind() Tile` ✅

**做什么** —— 把赤宝牌归一到对应的普通五（34→4、35→13、36→22），其余原样返回。

**为什么它是这个包最重要的约定** —— 赤五万在牌型上**就是**五万。凡是拿 `Tile` 做相等比较、当下标、当查表键的地方，都要先过 `Kind()`：

```go
counts[t.Kind()]++          // ✅  赤五万和五万进同一个桶
counts[t]++                 // ❌  分桶错误，而且不报错
if m.Tile() == winning {    // ❌  和牌张是赤五万时永远不成立
```

**卡在哪两个 choke point** —— `CountTiles` 与 `Hand.Counts`。规则层只读 `Counts`，所以 `Decompose` / 全部役种 / `CalcFu` 的**主体**都不用改。

⚠️ **`YakuContext` 的 `WinningTile` 与 `Melds` 不经过 `Counts`**，所以 `DetectYaku` 与 `CalcFu` 在入口各自调一次 `ctx.normalized()`。漏掉的症状是静默的：荣和赤五万补成的刻子会被算成暗刻（少 2 符还让三暗刻错误成立），嵌张的 +2 会丢。见 [规则集](规则集.md) §4。

#### `func NewTile(suit Suit, rank int) (Tile, error)` ✅

**做什么** —— 按花色和点数构造牌。数牌 `rank` 取 0–9（**0 表示该花色的赤五**），字牌取 1–7，越界报错。计算式是 `Tile(int(suit)*9 + rank - 1)`。

**为什么先校验再算** —— 这里踩过一个很隐蔽的坑：`Tile` 是 `uint8`，而 `rank` 是 `int`。如果先做算术再校验，**负数会回绕成巨大正数、大数会截断**：

| 调用 | 无校验时的结果 | 实际含义 |
| --- | --- | --- |
| `NewTile(SuitSou, -1)` | `Tile(7)` | 八万（错得毫无征兆） |
| `NewTile(SuitHonor, -1)` | `Tile(25)` | 八筒 |
| `NewTile(SuitMan, 260)` | `Tile(3)` | 四万 |

所以**校验必须在算术之前**，这是这个函数的全部要点。

**谁用** —— `ParseTiles`（每个数字都走它）、测试夹具、`MustTile`。

**赤牌的唯一入口** —— `NewTile(suit, 0)` 是构造赤五的唯一方式（`Tile(AkaMan5 + int(suit))`）。
**字牌没有赤牌，`NewTile(SuitHonor, 0)` 仍然报错。**

⚠️ **验收重点**：`Valid()` 接受 0..36、`Kind()` 对非赤牌恒等、`NewTile(suit, 0)` 只对数牌成立。
这三样写错的症状都出现在很远的地方。

#### `func MustTile(suit Suit, rank int) Tile` ✅

**做什么** —— `NewTile` 的 panic 版本，**内部转调 `NewTile`**（不重复实现转换逻辑）。

**谁用** —— 测试里写死的牌常量。

⚠️ **绝不可用于网络或用户输入**。名字里的 `Must` 就是这个约定。

#### `func (t Tile) Suit() Suit` ✅

**做什么** —— 返回花色。**先过 `Kind()`**，再按区段判断：`< 9` 万、`< 18` 索、`< 27` 筒、否则字牌。

**坑** —— **只对合法牌有意义**。`Tile(200)` 会落到 `SuitHonor` 分支，不会报错。调用前想清楚输入是否可信。

⚠️ **`Kind()` 不能省**。省掉的话 `Tile(34)`（赤五万）既不小于 27 也不是字牌区间内的合法值，会掉进 `SuitHonor` —— 赤五万变成"字牌"。

#### `func (t Tile) Rank() int` ✅

**做什么** —— 返回点数：数牌 1–9，字牌 1–7。实现是 `int(t.Kind())%9 + 1`。

⚠️ **赤五万返回 5，不是 0**。点数与"是不是赤的"是两回事，所以 `Rank()` 必须归一。

**为什么一个表达式通吃数牌和字牌** —— 因为**两段长度都是 9 的倍数**（数牌 0–26 共 27 个，字牌 27–33）。`27 % 9 == 0`，所以东（27）→ 1，中（33）→ 7，全对。这就是字牌点数常量要连号（1–7）的原因。

⚠️ 同样**只对合法牌有意义**。

#### `func (t Tile) IsNumber() bool` ✅

**做什么** —— 是否数牌。实现是 `t.Valid() && t.Kind() < numNumberKinds`。

**为什么需要** —— **只有数牌能组成顺子**。字牌不能。

**为什么带 `Valid()`** —— 否则 `Tile(255)` 会被判成"不是数牌"，进而被某些逻辑当成字牌处理，属于错误分类。

⚠️ **`Kind()` 不能省**。`IsHonor()` 也是。省掉的后果是**赤五万被当成字牌**：不能进顺子、被算进"字牌"的混一色/字一色判定，而这条错误只在手里有赤五万时出现。

#### `func (t Tile) IsHonor() bool` ✅

**做什么** —— 是否字牌。实现是 `t.Valid() && t.Kind() >= numNumberKinds`。

**为什么需要** —— 多条规则都以字牌为条件：宝牌指示范畴、混一色/清一色、混老头、字牌不能组顺子。

#### `func (t Tile) String() string` ✅

**做什么** —— 返回中文牌名，如 `"一万"`、`"东风"`、`"赤五万"`。非法牌返回 `"Tile(n)"`。

**谁用** —— 日志、错误消息、调试。

**为什么要有** —— 让日志能直接用。没有它，日志里全是 `Tile(12)`，排查问题等于翻译机器码。

⚠️ **两个名字表的长度不同（9 和 7），只能分支取**。写成"先取 `honorNames` 再覆盖"会直接 panic——九万的点数是 9，`honorNames[8]` 越界。

⚠️ **两处待改**：

1. **三元牌现在输出「白板/发财/红中」，项目决定改为「白/发/中」**。依据是雀魂、雀姬官方术语页与教程都以「白/发/中」为正名，「白板/发财/红中」只作为"读法"出现。风牌保留「东风/南风/…」不变。
2. **牌名用的是「索/筒」，而 README 与算分文档写的是「条/饼」**。项目决定统一到「索/筒」（改文档不改代码），README 需要加一句与任务书的映射说明。

#### `func FullSet() []Tile` ✅

**做什么** —— 返回一副完整的 136 张牌。

**赤宝牌在这里注入** —— 每种花色的五各有一张被**替换**成赤牌（M-League【M】第 2 章第 2 条 2），
所以种类数没变、总数仍是 136，只是其中 3 张的写码是 34/35/36。

**为什么赤牌张数写死在这里** —— `FullSet()` 拿不到 `Rules`。本项目照搬 M-League，
不做「无赤 / 三赤」变体，所以直接写死 1 张；`Rules.AkaDora` 只是让这条规则在代码里可见。
真要做变体时这里要改成 `FullSetFor(rules Rules)`。

**谁用** —— `NewWall` / `NewWallFromSeed` 的起点；测试里作为"张数守恒"的基准（`fullSetCounts()`）。

**注意** —— 返回的是**新切片**，每次调用都分配 136 字节。别在热路径上反复调。

## 2. `parse.go` —— 紧凑记法

**这一节的全部价值是：让测试夹具、日志和数据库共用同一种牌的文本表示。** 没有它，每个测试都要手写 `[]Tile{0,1,2}` 这种不可读的东西。

#### `func ParseTiles(s string) ([]Tile, error)` ✅

**做什么** —— 把 `"123m456s789p11z"` 解析成 `[]Tile`。规则：

- `m`/`s`/`p`/`z` 分别是万/索/筒/字牌
- 字母**前面**的数字是点数，可以一次写多个（`123m` = 三张）
- 同一个花色字母可以出现多次（`123m456m` 合法）
- 空白字符被忽略
- **结果保持书写顺序，不排序**

**赤五写作 `0`** —— `0m`/`0s`/`0p` 是该花色的赤五，`"055m"` = 赤五万、五万、五万。
`0` 由 `NewTile` 的 `rank == 0` 分支处理，解析器本身不需要特判。
**字牌没有赤牌，`"0z"` 报错。**

⚠️ **记法里没有两位数点数**，所以 `"10m"` 读作「一万 + 赤五万」而不是点数 10。
这在 `0` 变成合法点数之前是"报错"，现在是合法输入——不会静默吃掉任何东西，
但值得知道。

**为什么保持书写顺序** —— 因为顺序可能在业务上有意义（比如按摸到的先后）。要排序是调用者的事，用 `FormatTiles` 或自己排。

**谁用** —— 测试夹具（几乎所有测试）、数据库读回（`game_walls.tiles`、`game_initial_hands.tiles` 都是这个格式）、协议层。

⚠️ **它只校验语法，不校验张数上限**。`"11111m"`（同种 5 张）会**成功返回 5 张一万**。这不是疏忽，是刻意的分工：`parse.go` 的注释原话是

> 同种超过 4 张由 `CountTiles` 负责——否则就没有合法的输入能用来测它。

也就是说，**`CountTiles` 能独立存在并被测，靠的就是 `ParseTiles` 放行**。如果你"顺手"在这加个上限校验，`CountTiles` 的测试就再也构造不出触发条件了。

#### `func MustParseTiles(s string) []Tile` ✅

**做什么** —— `ParseTiles` 的 panic 版本。

**谁用** —— 测试里写死的牌组，例如 `MustParseTiles("123m456s789p11z")`。

⚠️ **绝不可用于网络或用户输入**。协议层拿到的字符串必须走 `ParseTiles` 并处理 error。

#### `func FormatTiles(tiles []Tile) string` ✅

**做什么** —— `ParseTiles` 的逆运算。按**万 → 索 → 筒 → 字牌**分组，组内按点数升序，输出如 `"123m456s789p11z"`。

**它不保持顺序** —— 这是它和 `ParseTiles` 的**关键不对称**：`ParseTiles` 保持书写顺序，`FormatTiles` 总是重新分组排序。所以 `FormatTiles(ParseTiles(s)) != s` 是正常的。

**赤五输出 `0`，且排在同点数的普通牌之前** —— `"055m"`。排序用的是 `Kind()`，
所以赤五万排在五万的位置上；直接用编号排的话赤五万会掉到整组的队尾（`"5550m"`）。

**非法牌被静默跳过** —— 因为它的用途是日志和调试输出，不该因为一张坏牌就 panic。

⚠️ **绝对不要用它做牌山的哈希输入。** 它按花色分组排序，会**丢掉摸牌顺序**——结果是所有"万牌组合相同"的牌山共用同一个指纹。牌山哈希必须用 `Wall.Bytes()`。

#### 未导出的小工具 ✅

| 函数 | 做什么 |
| --- | --- |
| `isCharSuit(r rune) bool` | `r` 是不是 `m`/`s`/`p`/`z` |
| `isCharNumber(r rune) bool` | `r` 是不是 ASCII `'0'`–`'9'` |
| `suitOfChar(r rune) Suit` | 记法字母 → `Suit`。**调用前须先用 `isCharSuit` 确认**，否则非花色字符会落到字牌分支 |
| `suitChar(s Suit) byte` | `suitOfChar` 的逆 |

**为什么 `isCharNumber` 是 `r >= '0' && r <= '9'` 而不是 `unicode.IsDigit`** —— `unicode.IsDigit` 对全角数字、阿拉伯-印度数字都返回真，会导致 `"１２３m"` 被接受。只认 ASCII 是刻意的。

⚠️ **这里踩过一个很隐蔽的坑**：早期版本 `FormatTiles` 用 `isCharNumber(byte(t))` 判断——把**牌的编号**当成 ASCII 数字判断。`Tile(0)` 是 `byte(0)`，不是 `'0'`（`0x30`），所以判断永远为假，输出只有花色字母没有数字（`"mmm"` 而不是 `"123m"`）。**编号 ≠ 字符**，这两个函数的参数类型是不同的东西。

## 3. `wall.go` —— 牌山

#### `type Wall struct { tiles []Tile }` ✅

**是什么** —— 一副洗好的 136 张牌，**按摸牌顺序排列**。字段私有，只能通过构造函数和 `Draw` 改变。

**为什么字段私有** —— 牌山的顺序是**可验证性的核心资产**。让它可被外部随意修改，等于让"玩家可以独立验证"这个承诺失效。

---

#### `func NewWallFromSeed(seed [32]byte) *Wall` ✅

**做什么** —— 用确定性种子构造牌山。同一个种子**永远**产出同一副牌山。

**为什么这是生产路径** —— 可验证性的地基就是"给定种子能重放"。玩家拿到 `serverSeed` 后自己跑一遍，就能验证服务器没有在洗牌时作弊。

**为什么种子是 `[32]byte` 而不是 `int64`** —— 数组注释里写明了：**种子要用满全部 32 字节**。只取其中一部分，候选空间会小到能被穷举——玩家拿到承诺值就能在开赛前把整副牌算出来，可验证性反而变成了漏洞。

**它内部怎么走** —— `FullSet()` → `Shuffle(tiles, rand.New(rand.NewChaCha8(seed)))`。注意是先造一副有序牌再洗，不是逐张随机抽——这样"张数守恒"是构造上保证的，不依赖算法正确性。

---

#### `func NewWall(r *rand.Rand) *Wall` ✅

**做什么** —— 用外部注入的随机源构造牌山。

**为什么与 `NewWallFromSeed` 并存** —— 注释写明：**前者服务测试，后者服务生产**。测试有时需要"随便一副牌"，不需要能重放，这时用注入的随机源方便固定或随意化。

⚠️ **不要用 `NewWall` 去发真牌局**——那样牌山不可复现，可验证性直接归零。

---

#### `func Shuffle(tiles []Tile, r *rand.Rand)` ✅

**做什么** —— 用 `r` 的字节流**就地**重排 `tiles`。降序 Fisher-Yates：`for i := len-1; i > 0; i--`，取 `j := int(r.Uint64() % uint64(i+1))`，交换 `i` 和 `j`。

**为什么不用标准库的 `rand.Shuffle`** —— 注释里的理由值得记住：

> 它从字节流映射到下标的方式属于实现细节，Go **不保证跨版本不变**，而验证要求多年后仍能重放。

这是整个包里最容易被"优化"掉的一处。换成 `rand.Shuffle` 会让所有历史牌局的验证**在某次 Go 升级后集体失效**，而且失效得很安静。

**关于取模偏差** —— `r.Uint64() % (i+1)` 对不是 2 的幂的 `i+1` 会有轻微偏差（除不尽）。注释里明确接受：**不发奖的牌局无所谓**。这不是疏忽，是权衡后的决定。想消除得用拒绝采样，会让重放逻辑变复杂。

---

#### `func (w *Wall) Remaining() int` ✅

**做什么** —— 还没摸走的张数。

**注意实现** —— 用 `len(w.tiles)`，**不是 `len(w.Tiles())`**。后者会为了一个长度而复制 136 个元素——这个错误犯过。

---

#### `func (w *Wall) Empty() bool` ✅

**做什么** —— 牌山是否摸空。就是 `Remaining() == 0`。

**为什么值得单独一个方法** —— 因为"摸空"是**正常业务分支**（该小局荒牌流局），不是异常。有个语义明确的方法名，调用点读起来就清楚。

---

#### `func (w *Wall) Draw() (Tile, bool)` ✅

**做什么** —— 从牌山头部取一张。空了返回 `(0, false)`。

**它改变状态** —— 这是 `Wall` 上唯一的可变方法。

**实现细节** —— `w.tiles = w.tiles[1:]`，**只前移切片头，不复制底层数组**。

⚠️ **这里踩过一个会让整个包静默失效的坑**：早期版本写的是 `w = &Wall{tiles: w.tiles[1:]}`——**重新赋值了局部接收者变量**，牌山本身一张没少。表现为 `Draw()` 两次拿到同一张牌，且 `Remaining()` 一直是 136。Go 的接收者是值传递（即使是指针接收者，指针变量本身也是拷贝），**改接收者变量 ≠ 改它指向的对象**。

---

#### `func (w *Wall) Tiles() []Tile` ✅

**做什么** —— 返回完整摸牌顺序的**副本**。

**为什么必须返回副本** —— 否则调用者 `sort` 一下就把牌山毁了。而且这种破坏是静默的——牌山看起来还在，只是顺序变了。同类的三处都在 `hand.go`（`NewHand` 拷入参、`Tiles()` 返回副本、`Clone()` 深拷贝）。

**和 `Sequence()` / `Bytes()` 的区别** —— 这个返回 `[]Tile`（机器用），那两返回字符串和字节（存储/哈希用）。

---

#### `func (w *Wall) Bytes() []byte` ✅

**做什么** —— 返回 136 字节，**每字节是一张牌的编号**，按摸牌顺序。

**谁用** —— `verify.go` 的 `WallHash`：`SHA256(w.Bytes())`。

⚠️ **它的存在就是为了让 `FormatTiles` 不被误用。** 函数注释直接写了警告：`FormatTiles` 按花色分组排序，会丢掉顺序，**导致所有同花色组合的牌山共用同一个指纹**。牌山指纹必须建立在"顺序"之上。

---

#### `func (w *Wall) Sequence() string` ✅

**做什么** —— 按摸牌顺序**逐张**写成紧凑记法，例如 `"1m5p3s2z..."`，共 136 组。

**和 `FormatTiles` 的关键区别**：

| | `FormatTiles` | `Wall.Sequence` |
| --- | --- | --- |
| 顺序 | 分组 + 组内排序 | **保持摸牌顺序** |
| 输出 | `"123m"`（合并同类） | `"1m2m3m"`（逐张一个字母） |
| 丢信息 | 是 | 否 |

**谁用** —— 入库（`game_walls.tiles` 存的就是它）、人工核对、前端验牌页。

**往返性** —— 输出可被 `ParseTiles` 原样读回（`"1m2m3m"` 解析成三张万）。这是它选择"逐张一个字母"而不是紧凑形式的原因。

---

#### `func (w *Wall) Deal() ([4][]Tile, error)` ✅

**做什么** —— 给四家**各发 13 张**，返回值的索引就是座位号 `0..3`。发完剩 84 张。

**⚠️ 这里有一个与任务书不一致的刻意设计**：任务书写"庄家分到 14 张"，但 `Deal` **只发 13 张**，庄家的第 14 张由房间层调用 `Draw` 取得。

**为什么这么设计** —— 函数注释里的理由：

> 这样 `Deal` 不必知道庄家是谁，庄家轮换（第 N 小局的庄家为玩家 N）交给房间层。

也就是说，把"谁是庄家"这个**每局都在变的信息**挡在 `mahjong` 包外面。最终四家手上的牌和任务书完全一致，只是**第 14 张出现在 `draw` 事件里而不是 `deal` 事件里**。

**对数据库的影响** —— `game_initial_hands` 存的是四家各 13 张，庄家第 14 张是 `game_events` 里的一条 `draw`。

⚠️ **这里也踩过一个坑**：早期版本在循环里 `hands[i] = make([]Tile, 13)`，把已追加的牌覆盖掉了。表现是"共发出 53 张但四家手牌合计 52 张"——差的正好是庄家那第 14 张（当时的设计）。修复方式是每个座位只分配一次。

**错误分支** —— 余牌不足 52 张时返回错误。注意 `if !ok` 那个防御分支**永远不会触发**（前置检查已保证够发），它是 0.8% 未被覆盖的代码里的一部分。

---

## 4. `hand.go` —— 手牌容器 ⚠️

> **这个文件只差一个函数。** `Count`、`Tiles`、`Counts` 都已写好，唯一没完成的是 `CanWin`（空函数体，缺 `return`），它是目前 `go build` 唯一的报错点。详见 §8。

#### `type Hand struct { tiles []Tile }` ✅

**是什么** —— **可变的**手牌容器。与 `Wall` 的区别：牌山只能从头部拿走（不允许乱序），手牌可以任意增删。

**为什么不用裸 `[]Tile`** —— 三个理由：① 可以挂方法；② 把"增删"的语义（比如 `Remove` 只删一张）固定下来；③ 提供**受控的拷贝语义**，这是房间层做快照的前提。

**为什么不做成不可变** —— 对局中摸打频繁，每次不可变都要分配。这里选可变 + 显式 `Clone`。

---

#### `var ErrTileNotFound, ErrHandFull` ✅

**是什么** —— 两个哨兵错误。

**为什么用哨兵** —— 让上层能用 `errors.Is(err, ErrTileNotFound)` 分类处理，而不是靠字符串匹配。协议层需要据此决定回哪个错误码（`TILE_NOT_IN_HAND`）。

⚠️ **`ErrHandFull` 目前没人用**。Go 对包级变量不报"未使用"，所以能编译，但它暗示 `Add` 本该有个上限（手牌最多 14 张）。要么在 `Add` 里用上，要么删掉。

---

#### `func NewHand(tiles []Tile) *Hand` ✅

**做什么** —— 构造手牌，**拷贝入参**。

**为什么必须拷贝** —— 否则调用者改自己的切片会连带改掉手牌。这类 bug 在房间层会表现为"改了一个快照，结果原手牌也变了"——极难定位，因为两处代码各自看都没问题。

#### `func (h *Hand) Add(t Tile)` ✅

**做什么** —— 加一张牌到末尾。

**为什么没有返回值** —— 加牌不会失败（`Tile` 是 `uint8`，任何值都能存进去）。

⚠️ **这意味着 `Hand` 里可能存进非法牌**。`Counts()` 因此必须做 `Valid()` 守卫，见下。

#### `func (h *Hand) Remove(t Tile) error` ✅

**做什么** —— 删掉**一张** `t`。找不到返回 `ErrTileNotFound`。

**「只删一张」是核心约定** —— 手上有三张一万，打出一张后还剩两张。删之前不检查数量是否足够，调用方（房间层）负责保证。

**失败时不改变手牌** —— 这个性质让调用方可以"试着删，失败就走另一条分支"。

**返回值是裸哨兵而非包装** —— `return ErrTileNotFound` 直接返回哨兵，`errors.Is` 照样匹配。文档说"要用 `fmt.Errorf("%w: ...")` 包装"，包装是为了附加上下文（比如"哪张牌不在手里"）；裸返回哨兵也满足 `errors.Is` 的要求，只是错误消息里没有牌名。

**实现** —— `append(h.tiles[:i], h.tiles[i+1:]...)`。这会**就地修改底层数组**，并把末尾元素复制一份留在数组尾部（对 `Tile` 这种值类型无害）。

#### `func (h *Hand) Len() int` ✅

**做什么** —— 张数。

**为什么需要它** —— 手牌在游戏中合法张数只有 13（待摸）或 14（摸完未打），房间层要据此校验状态机。

#### `func (h *Hand) Count(t Tile) int` ✅

**做什么** —— 手上**某种牌**有几张（0–4）。

**和 `Counts()` 的区别** —— `Count` 问"这一种有几张"，`Counts()` 一次性给出全部 34 种的分布。前者适合"顺便问一句"，后者适合"要跑算法"。

**谁用** ——

- **杠的合法性**：暗杠要先确认手里有 3 张（加杠是 1 张）
- **宝牌计数**：算番时要数手里每种宝牌有几张
- **符数计算**：判断刻子是明刻还是暗刻、是中张还是幺九

**实现** —— 线性扫描。手牌最多 14 张，不值得上哈希表。

```go
func (h *Hand) Count(t Tile) int {
	n := 0
	for _, tile := range h.tiles {
		if tile == t {
			n++
		}
	}
	return n
}
```

#### `func (h *Hand) Tiles() []Tile` ✅

**做什么** —— 返回**排序后的副本**。

**为什么要排序** —— 手牌在界面上和日志里都是有序显示的；也方便用 `reflect.DeepEqual` 比较两个手牌。

**为什么要副本** —— 同 `NewHand` 的理由。

**当前实现**：

```go
func (h *Hand) Tiles() []Tile { // 排序后的副本
	tiles := append([]Tile(nil), h.tiles...)
	sort.Slice(tiles, func(i, j int) bool {
		return tiles[i] < tiles[j]
	})
	return tiles
}
```

⚠️ **这里踩过两个坑，都值得记住。**

**坑一：闭包索引了错误的切片。** 早期版本的闭包写的是 `h.tiles[i] < h.tiles[j]`——**比较的是原切片，而不是被排序的那个副本**。`sort.Slice` 传进去的是副本，闭包收到的 `i`/`j` 是**副本的下标**，拿去索引原切片等于"按一份从未改变的数据，去排一个不再被读取的数组"，**输出不保证有序**。

> **通用规则**：`sort.Slice` / `slices.SortFunc` 的闭包里索引的切片，必须和传进去的那个是同一个。名字不一样就停下来看一眼。

**坑二：`sort.Slice` 没有返回值。** 早期版本写成 `res := sort.Slice(...)`。它的签名是 `func Slice(x any, less func(i, j int) bool)`——**只有副作用，没有返回值**。

用 `sort.Slice` 和 `slices.Sort` 都可以：`Tile` 的底层类型是 `uint8`，满足 `cmp.Ordered`，`slices.Sort(tiles)` 同样成立（`parse.go` 里用的就是它）。

#### `func (h *Hand) Counts() Counts` ✅ ⚠️

**做什么** —— 返回整手牌的**直方图**（34 长度的计数数组）。

**为什么这是整份文档里最重要的一对函数之一** —— 因为 `win.go` 的判定算法**不在 `[]Tile` 上跑，在 `Counts` 上跑**。原因见 §5 的 `CountTiles`。

**谁用** —— `Decompose`、`DetectYaku`、`CalcFu` 的入口。

**当前实现**：

```go
func (h *Hand) Counts() Counts { // 统计每种牌的数量
	counts := Counts{}
	for _, tile := range h.tiles {
		counts[tile]++
	}
	return counts
}
```

**为什么不用 `CountTiles`** —— `CountTiles` 返回 `(Counts, error)`，而这里签名没有 error。把 error 吞掉会掩盖问题，所以选择直接累加、不做校验。

⚠️ **缺一个越界守卫。** `Counts` 是 `[34]int`，而 `Tile` 只是 `uint8`——一个 `Tile(200)` 进来就是 `panic: index out of range`。

这条路径**目前打不通**（`ParseTiles` 只产出合法牌，`NewTile` 会挡掉越界），但 `Add(t Tile)` 无返回值、`NewHand([]Tile)` 也不校验，所以守卫是否必要，取决于你打算**在哪里**保证"手牌里只有合法牌"这个不变量。三种选择：

| 做法 | 代价 |
| --- | --- |
| 加 `if tile.Valid()` 静默跳过 | 坏牌被无声吞掉，将来更难查 |
| **让 `Add` 返回 error** | 签名变重，但把不变量挡在入口；顺带用上闲置的 `ErrHandFull` |
| 什么都不做，靠调用方保证 | 最轻，但包将来在服务端跑，炸的是整个进程 |

我倾向**第二种**——在入口挡住比在出口补救干净。注意它和 §8 第 4 条（`ErrHandFull` 无人使用）是同一个问题：`Add` 本来就该有个失败路径，加上上限检查和合法性检查，`ErrHandFull` 就有归宿了。

#### `func (h *Hand) CanWin() bool` ⬜ ★ 当前的编译阻塞点

**做什么** —— 便利方法，等价于 `CanWin(h.Tiles())`。

**为什么要有** —— 让调用点写成 `hand.CanWin()` 而不是 `mahjong.CanWin(hand.Tiles())`。代价是 `CanWin` 这个名字在包里出现两次（方法 + 函数），Go 允许，但读代码时要分清。

**现状** —— 函数体是空的，`bool` 没有 `return`。这是 `go build` 目前**唯一**的报错：`hand.go:66:1: missing return`。

⚠️ **不要直接写 `return CanWin(h.Tiles())`。** `win.go` 里的 `CanWin` 目前只有签名没有实现（见 §5），直接调用会把"编译错误"变成"链接错误"，报错位置反而离这行更远。先把 `win.go` 那四个函数补上体。

#### `func (h *Hand) Clone() *Hand` ✅

**做什么** —— 深拷贝。

**谁用** —— 房间层做"出牌前快照"、模拟走棋、悔棋。`mahjong` 包自己不用。

**为什么是它而不是 `NewHand(h.Tiles())`** —— `Clone` 不排序，保留原始顺序；而且意图更明确。

## 5. `win.go` —— 和牌判定 ⚠️

> **`win.go` 目前只有类型和函数签名，那四个函数没有函数体，编译不过。** 这一节解释的是**为什么需要这些函数**，实现方式见 [实现指南](实现指南.md) §1.5。
>
> ⚠️ **Go 不允许「只有签名没有函数体」的普通函数。** 下面这种写法只在两个场合合法：**用汇编实现**，或者**用 `//go:linkname` 之类的外部实现**。普通函数必须给个函数体——哪怕是 `panic("TODO")`。
>
> ```go
> func CountTiles(tiles []Tile) (Counts, error)   // ← 这样写编译不过
> ```
>
> **实测结果**：`hand.go` 的类型错误**挡住**了 `win.go` 的报错。补上 `hand.go:66` 之后，`win.go` 会一次报出 **4 条** `missing function body`（第 5、27、28、29 行）。
>
> **但 `Counts` 类型本身是对的**——`hand.go` 的 `Counts()` 已经能正常用它。真正编译不过的只有那四个没有体的函数。
>
> **推荐的空体写法**：
>
> ```go
> func CountTiles(tiles []Tile) (Counts, error) {
> 	panic("mahjong: CountTiles 尚未实现")
> }
> ```
>
> **不要写 `return Counts{}, nil` 这种假返回值**——那会让未实现的部分**静默返回错误答案**，测试有可能"通过"，问题会留到很远的地方才爆。`panic` 保证任何调用都立刻、响亮地失败。

#### `type Counts [NumTileKinds]int` ✅

**是什么** —— 34 长度的计数数组。`Counts[5]` = 手上有几张六万。

**为什么整个算法要基于它，而不是 `[]Tile`** —— 这是本包最核心的设计决定。`win.go` 的算法是"枚举雀头 → 拆面子 → 回溯"。在 `[34]int` 上：

| 操作 | 在 `Counts` 上 | 在 `[]Tile` 上 |
| --- | --- | --- |
| 拿掉一对当雀头 | `c[i] -= 2` | 查找两个位置、删除、记住下标 |
| 拿掉一个刻子 | `c[i] -= 3` | 同上，三个位置 |
| 拿掉一个顺子 | `c[i]--; c[i+1]--; c[i+2]--` | 三次查找 |
| **回溯恢复** | `c[i] += 2` | **按记住的下标逐个插回** |

前三种在 `Counts` 上都是 O(1)。第四种是关键——**回溯的"恢复"步骤是手写算法最容易出错的地方**，而 `Counts` 上它就是一次加法，不可能写错。

用 `[]Tile` 的话，你需要维护"哪些下标被拿走了"的簿记，分支一多必然有路径忘了恢复。这就是 [实现指南](实现指南.md) §1.5 里列的第一个坑："回溯忘记恢复计数"。

**为什么是数组而不是 `map[Tile]int`** —— 数组是值类型，传参、复制、比较都直接；`map` 是引用类型，回溯时会互相污染，而且有哈希开销。

**代价** —— `Counts` 丢掉了顺序信息。这对和牌判定无关（手牌顺序不影响能否和牌），但**不能拿它做牌山哈希**（同 `FormatTiles` 的问题）。

#### `func CountTiles(tiles []Tile) (Counts, error)` ⬜

**做什么** —— 从任意切片构造 `Counts`，**并校验**：非法牌、同种超过 4 张。

**为什么需要一个带校验的版本** —— 因为 `Hand.Counts()` 不带校验（见 §4）。分工是：

| | 校验 | 面对什么输入 |
| --- | --- | --- |
| `Hand.Counts()` | 否 | `Hand` 内部，来源受控 |
| `CountTiles` | **是** | 解析器输出、测试夹具、对局快照等**不可信输入** |

**为什么它能独立存在** —— 因为 `ParseTiles` **刻意不校验 4 张上限**（§2），把这件事留给它。否则 `CountTiles` 的校验分支**永远构造不出触发它的输入**，那段代码就没法测。这是一个"为了让代码可测而划分职责"的例子。

**错误分支** —— `"11111m"`（同种 5 张）、`Tile(255)`（非法牌）都要返回错误。

#### `type MeldKind uint8` + `MeldRun` / `MeldTriplet` / `MeldKan` ✅

**是什么** —— 面子类型：顺子 / 刻子 / 杠。

**为什么杠单独一类** —— 杠在**符数**（明杠 8/16、暗杠 16/32，刻子是 2/4/4/8）和**役种**（三杠子、四杠子、岭上开花）上都与刻子不同，所以必须能区分。但在**和牌型判定**上杠和刻子一样占一组面子——这个"同一个概念在两层里含义不同"的地方要小心。

#### `type Meld struct { Kind; Tiles [4]Tile; IsOpen bool }` ✅

**是什么** —— 一组已组成的面子。

| 字段 | 含义 |
| --- | --- |
| `Kind` | 顺子 / 刻子 / 杠 |
| `Tiles` | 组成它的牌。顺子/刻子用前 3 个，杠用满 4 个 |
| `IsOpen` | 是否副露（**含荣和组成的那一组**） |

**为什么 `Tiles` 是 `[4]Tile` 定长数组** —— 因为一组面子最多 4 张（杠）。用数组避免切片分配，而且长度语义固定。

**⚠️ `IsOpen` 的"含荣和组成的那一组"这一条极易漏** —— 荣和的那张牌组成的刻子算**明刻**。它同时影响两件事：**「三暗刻」「四暗刻」是否成立**，以及**符数**（明刻 2/4 符 vs 暗刻 4/8 符）。这是 [实现指南](实现指南.md) §1.6 和 §1.7 都专门列出的坑。

#### `type Decomposition struct { Pair Tile; Melds []Meld }` ✅ ⚠️

**是什么** —— 一种**完整的拆法**：一个雀头 + 若干面子。

**为什么叫"拆法"而不是"牌型"** —— 因为**同一个牌型可以有多种拆法**，而不同拆法会导致不同的役种和符数：

```
111222333m  →  拆成三个刻子：可能成立「三暗刻」
            →  拆成三个顺子：可能成立「一杯口」「平和」
```

**`Shape` 字段（已加入）** —— 和牌形只有三种（标准型 / 七对子 / 国士无双）。没有它，`DetectYaku` 就**看不到七对子与国士**——而七对子是 **2 翻 25 符的普通役**，不能像国士那样单独开一路。七对子表示成「`Pair` 一对 + `Melds` 里 6 个 `MeldPair`」，与标准型共用同一套 `Pair + Melds` 语义，所以 `Decomposition.Tiles()` 对三种形态一视同仁。
```go
type Shape uint8
const ( ShapeStandard Shape = iota; ShapeChiitoitsu; ShapeKokushi )

type Decomposition struct {
    Shape Shape
    Pair  Tile
    Melds []Meld
}
```

**`Shape` 还顺手解决了另外两件事**：`DetectYaku` 不用在外面重判一遍形态；`Decompose` 可以对三种形态一视同仁地返回。

#### `func Decompose(tiles []Tile) ([]Decomposition, error)` ⚠️

> 文档原写的签名是 `func Decompose(tiles []Tile) []Decomposition`。实现里为了上抛 `CountTiles` 的错误，改成了返回 `err`。**两处要同步一处**——改了代码就改文档，或者反过来。

**做什么** —— 返回**全部**合法拆法。

**为什么是"全部"而不是"任意一种"** —— 这是完整规则相对简化版最重要的接口变化。简化版只问"能不能和"，完整规则要问"**按哪种拆法算分最高**"——所以上层要拿每个候选去跑 `DetectYaku`，取分最高者。

**也因此它不能提前 `return`** —— 递归时要收集而不是短路返回。

**候选数量** —— 一副 14 张牌最多几十种拆法，全收集没有性能问题。

**七对子的等价性** —— `11223344556677m` 既是七对子，也能拆成标准型（`123m 123m 456m 456m + 77m`）。**两种都要产出**，由上层择优。

**⚠️ 它要接受任意 `3k+2` 张，不只是 14 张。** 有 M 个副露时，暗牌是 `14 − 3M` 张：

| 副露数 M | 暗牌张数 | 要拆成 |
| :--: | :--: | --- |
| 0 | 14 | 4 面子 + 雀头 |
| 1 | 11 | 3 面子 + 雀头 |
| 2 | 8 | 2 面子 + 雀头 |
| 3 | 5 | 1 面子 + 雀头 |
| 4 | 2 | 0 面子 + 雀头（四杠子，只剩雀头） |

**张数本身就决定了 `k`，所以 `Decompose` 不需要知道副露有几个。**

> **修正**：我早先建议过 `Decompose(tiles, melds)`。那是错的——**形状判定不需要副露**。副露只在**役种判定**时才需要（三色同顺、一气通贯、混一色、三杠子都横跨副露与暗牌），所以它们属于 `YakuContext`，不属于 `Decompose` 的参数。

**⚠️ 杠不参与拆解。** 杠是"摆到边上 + 补一张岭上牌"，手上少 3 张，与碰**完全等价**（碰 −2 出手；杠 −3 出手 +1 补牌）。所以 **`MeldKan` 只会出现在副露列表里，`Decompose` 永远不产出它**——暗牌里不可能"拆出"一个杠。

更细的推论见 [规则集](规则集.md) §13.1。

**⚠️ 暗牌里出现 4 张同种是合法的，不是错误。** 例：`111123m 456m 789m 11p` 能和牌（`111m` + `123m` + `456m` + `789m` + `11p`，用了四张一万）。所以遇到 `counts[i] == 4` 要**正常回溯**（试刻子剩 1、试顺子剩 3），既不能报错，也不能当成"这里有杠"。

`CountTiles` 那条「同种 > 4 非法」是**物理约束**（一副牌只有 4 张），不是**形状约束**。两者别混。

**⚠️ 枚举雀头时别踩 Go 的 `range` 坑。** 这个写法是错的：

```go
for _, c := range counts {
    if c >= 2 {
        counts[c] -= 2   // ← c 是"张数"(0..4)，不是牌的编号
        ...
    }
}
```

`for _, c := range counts` 里的 `c` 是**值**（某种牌的张数），不是下标。`if c >= 2` 碰巧对，但 `counts[c]` 索引的是编号 0–4 的牌。要写成 `for i, c := range counts` 并用 `counts[i]`。

#### `func CanWin(tiles []Tile) bool` ⬜

**做什么** —— 能否和牌。等价于 `len(Decompose(tiles)) > 0`（拆法里已含七对子与国士两种形态）。

**谁用** —— 房间层判断"打出的牌有没有人能和"。

⚠️ **它只回答"形状能不能和"，不回答"有没有役"，也不回答"是不是振听"。** 三个条件在房间层必须都查——见 [规则集](规则集.md) §2。

#### `func CanWinWith(hand []Tile, t Tile) bool` ⬜

**做什么** —— 判定"手牌 + 一张新牌"能否和牌。荣和判定的入口。

⚠️ **它不修改传入的 `hand`**。这个要求被单独列进验收清单，因为最自然的实现是 `hand = append(hand, t)` 再判定——那会**就地改写调用者的底层数组**。

#### `func Waits(hand []Tile) []Tile` ⬜ ★ 引入的缺口

**做什么** —— 返回能让 `hand` 和牌的全部牌种，按编码升序；空切片表示未听牌。

**为什么要独立一个函数** —— 它有三处**互相独立**的下游依赖，缺了它三处都会各自手写一遍遍历：

| 下游 | 用途 |
| --- | --- |
| **振听判定** | 要维护"自己的舍牌里有没有听牌张"（永久振听）<br>以及"刚才放过的牌是不是听牌张"（同巡振听） |
| **听牌料**（[规则集](规则集.md) §11.1） | 荒牌流局时要判定四家谁听牌 |
| **立直宣言的合法性** | 立直的前提就是听牌 |

**算法上没有新东西** —— 遍历 34 种牌，逐张问 `CanWinWith(hand, t)`。所以**它的正确性完全建立在 `Decompose` 之上**：`Decompose` 错，听牌判定就一起错。

**边界** —— 手牌张数不是 `3k+1`（听牌时的形状）时返回空切片。

**⚠️ 首巡的九种九牌用不到它** —— 那个判定只数幺九牌的种类数，与听牌无关。

#### `func IsTenpai(hand []Tile) bool` ⬜

**做什么** —— 等价于 `len(Waits(hand)) > 0`。便利方法。

**⚠️ 振听不影响它。** 振听的人**照样算听牌**，照样照收听牌料。这两件事用的是同一套听牌判定，但**不要把听牌判定和和牌判定混起来**——它们是同一个 `Waits` 的两个不同下游。

#### `func TenpaiSeats(hands [4][]Tile) [4]bool` ⬜

**做什么** —— 一次判定四家的听牌状态，供荒牌流局结算用。

**为什么值得单独一个** —— [规则集](规则集.md) §11.1 的听牌料不是"谁听牌谁赢 1000"那么简单，而是「未听牌者合计支付 3000，由听牌者均分」，先要拿到四家的布尔数组才能算。放在 `mahjong` 里是因为它是纯函数，放房间层会让那段结算逻辑无法单测。

## 6. `yaku.go` 及 `yaku_*.go` ✅ / `fu.go` ✅ / `score.go` ✅ / `dora.go` ✅

> 役种表、符数表、点数表**一律以 [规则集](规则集.md) 为准**，不要在这里重抄一遍——两处表述一定会漂移，漂移之后没人知道哪份是对的。

### 6.1 `yaku.go` 与 `yaku_*.go`

#### `type Yaku struct { Name string; Han int; HanOpen int; Yakuman int }` ⬜

**是什么** —— 一个役种的静态定义。

| 字段 | 含义 |
| --- | --- |
| `Name` | 中文名，如 `"立直"` |
| `Han` | **门清时**的翻数 |
| `HanOpen` | 副露时的翻数；**`-1` 表示门清限定** |
| `Yakuman` | 役满倍数；`0` 表示非役满 |

**为什么用 `-1` 而不是 `0` 表示门清限定** —— 因为 `0` 已经被"这个役在副露时不计翻"占用了（比如宝牌不是役）。用哨兵值把"完全不成立"和"成立但 0 翻"分开，`DetectYaku` 才能正确地"遇到副露直接跳过"。

#### `type YakuHit struct { Yaku Yaku; Han int }` ⬜

**是什么** —— 一次判定中命中的役，`Han` 是**本次实际计几翻**。

**为什么需要它而不是直接用 `Yaku.Han`** —— 因为有些役的翻数**取决于上下文**，不是固定的。同一个役种在不同情境下可能算不同的翻。

#### `type YakuContext struct { ... }` ⬜

**是什么** —— 判定役种所需的全部外部信息：门清、自摸、立直、一发、岭上、抢杠、海底、河底、场风、自风，外加 **`WinningTile Tile`（和牌的那张）** 与 **`Melds []Meld`（副露）**。

**为什么要把它们打包成一个结构体** —— 否则 `DetectYaku` 会有十几个参数。更重要的是：**这个结构体就是"役种判定依赖哪些外部状态"的完整清单**，一眼能看出边界。

**五个容易写错的地方**：

- **`Melds []Meld`（已加入）** —— **已副露**的面子（含杠）。**大量役横跨副露与暗牌**：三色同顺可能是一组暗顺 + 两组副露顺；混一色要数全部牌（含副露里的）；三杠子要数杠的个数；平和要求四个面子全是顺子——副露的算不算也要看。所以它挂在 `YakuContext` 上，而不是 `Decomposition`（后者只有暗面子）。
- **`WinningTile` 同时被 `DetectYaku` 和 `CalcFu` 需要，所以放在 context 而不是当参数。** `DetectYaku` 用它判平和的**两面听**、`CalcFu` 用它判**待ち形**（单骑/嵌张/边张/两面）与**荣和那张组成的刻子算明刻**。早先 `CalcFu(d, ctx, winningTile)` 把它单列成参数，等于同一条信息有两个来源——`CalcFu` 从 ctx 里读，调用方就再也传不进一个和 ctx 不一致的值。
- **`IsMenzen` 应当由副露推导，不要让人手填。** 判据是「所有副露都是暗杠」——**暗杠不破门清**。别写成"有任何副露就不是门清"。这个字段传错的症状极隐蔽：役种少了一个，但不知道少的哪个。
- **`RoundWind` / `SeatWind` 都是 `Tile`**：役牌要**按场风 + 自风**判定。**连风牌**（东场东家摸东）**两个役牌役都成立，共 2 翻**——不是 1 翻。
- **`Yakuman > 0` 时其余字段全部失效**：役满优先级最高，翻数和符数都不参与计算。

#### `func DetectYaku(d Decomposition, ctx YakuContext) []YakuHit` ⬜

**做什么** —— 给定一种拆法 + 上下文，返回**命中的全部役种**。

**为什么是"全部"而不是"最高分的那一个"** —— 因为多个役可以叠加，总翻数是求和。选最高分是上层的事（对每种拆法求和，再取最大）。

**返回空切片表示无役** —— 上层据此判定"不能和牌"，并回 `ILLEGAL_ACTION`。

⚠️ **宝牌不在这里**。宝牌不是役，在点数换算时才加。如果在这里当成役处理，就会出现"只有宝牌也能和牌"的错误。

### 6.2 `fu.go`

#### `func CalcFu(d Decomposition, ctx YakuContext) int` ✅

**做什么** —— 给定拆法 + 和牌方式 + 和牌张，算出符数。

**和牌张从 `ctx.WinningTile` 读，不再单列参数** —— 理由见 §6.1。它决定**待ち形**（两面/嵌张/边张/单骑），也决定**荣和的那张牌组成的刻子算明刻**。

**为什么和 `DetectYaku` 完全独立** —— [实现指南](实现指南.md) §1.7 明确要求："符算符，役算役，最后在点数换算那里汇合。"理由是两边的算法没有共享结构，耦合只会让两边都难改。

**两个必须单独处理的特例**：

- **七对子固定 25 符**（不取整）
- **平和自摸固定 20 符**（**不加**自摸的 2 符）

**取整只做一次** —— 所有加符项累加完之后向上取整到 10 符。分次取整会累积误差。

### 6.3 `score.go`

#### `type Rules struct { KiriageMangan; Kuitan; AkaDora; Pao; Renhou; KazoeYakuman; DoubleYakuman }` ✅

**是什么** —— 规则配置。**本项目照搬 M-League**，所以它**不是"变体开关板"**——字段固定为 M-League 的值，列出来是为了让「我们用了哪套规则」在代码里**可见**。完整清单与出处见 [规则集](规则集.md) §14.4。

**为什么还是要一个结构体而不是写死常量** —— 一是测试可以构造不同配置来验证边界；二是将来若换规则集，改动集中在一处，不用翻遍 `yaku.go` / `fu.go` / `score.go`。

#### `func DefaultRules() Rules` ✅

**做什么** —— 返回本项目的默认规则。

**为什么需要一个显式默认值** —— 否则"默认"这个概念的实现散落在各处零值上，改默认值要翻遍代码。

#### `const NoSeat = -1` ✅

**是什么** —— 「没有这个座位」。自摸时没有放铳者，也没有帕奥责任者；两处都用它，而不是 `0`——**`0` 是一个合法的座位号**（起家）。

#### `type ScoreInput struct { ... }` ✅

**是什么** —— 一次和牌算分所需的全部输入。字段分四组：

| 组 | 字段 | 说明 |
| --- | --- | --- |
| 点数 | `Han` `Fu` `Yakuman` | `Han` 是**总翻数**（役 + 宝牌 + 里宝 + 赤宝），**不含場ゾロ** |
| 座位 | `WinnerSeat` `LoserSeat` `DealerSeat` | `LoserSeat` 自摸传 `NoSeat` |
| 方式 | `IsTsumo` | |
| 加算 | `Honba` `RiichiSticks` | 立直棒**全部归和牌者** |
| 帕奥 | `PaoSeat` `PaoYakuman` | 见下 |

**为什么是一个结构体而不是一长串参数** —— 算分要同时知道**谁和牌、谁放铳、谁是庄**，而这三个座位号决定了每一笔付给谁。散成位置参数时，调用方极容易把 `winnerSeat` 和 `dealerSeat` 传反——**那种错误不会报错，只会把点数算到别人头上**。

⚠️ **`DealerSeat` 必须显式传，不能假定 `0`。** `seat 0` 是**起家**，庄家每小局轮换。最早的一版 `CalcScore` 就是把「座位 0 = 庄家」写死了。

⚠️ **`PaoSeat` 与 `PaoYakuman` 是「帕奥那一个役满」的倍数，不是总倍数。** `Yakuman` 是总倍数，`PaoYakuman` 是其中该由责任者承担的那部分，其余部分照常结算。

#### `func BasePoints(han, fu, yakuman int, rules Rules) int` ✅

**做什么** —— 返回**基本点**（已按 [规则集](规则集.md) §7 封顶）：`符 × 2^(2+翻)`。

**为什么导出** —— 为了让测试能**直接对着基本点断言**，而不必绕过支付规则间接验证。点数速查表的错**几乎都出在这一层**，不是出在支付规则。

**封顶顺序** —— 役满 → 三倍满（实翻 11+）→ 倍满 → 跳满 → 满贯 → 切上满贯的两个临界值。

#### `func Ceil100(n int) int` ✅

**做什么** —— 向上取整到百位。

⚠️ **每一笔支付要分别调用，不是先求和再取整。** 见下。

#### `func CalcScore(in ScoreInput, rules Rules) [4]int` ✅

**做什么** —— 返回**四个座位各自的收支**，按座位索引，已含本场与供托。

**为什么返回 `[4]int` 而不是 `[]Payment`** —— 四个人永远存在。用定长数组让「每个座位都有一个数」成为**类型事实**，而且守恒式可以**无条件断言**。早先设想的 `[]Payment` 只列出变化的座位，会让「荣和时另两家不动」和「忘了写这两家」在结果里长得一模一样。

⚠️ **守恒式是 `sum(返回值) == 1000 × RiichiSticks`，不是 `sum == 0`。**
立直棒**不是一笔转账**——它在宣言时就已经从某人分数里扣掉进了供托，`CalcScore` 只是把它记回和牌者名下，所以四家总和会增加那么多。不含立直棒时才退化成 `sum == 0`。
测试里随机造两万组输入核对这条（`TestCalcScoreConservation`）。

⚠️ **帕奥时本场棒全部由责任者出**，不是三家分摊（【M】第 8 章第 1 条 2「積み場は鳴かせた者が負担する」）。官方复合役满例子里西家的 −40300 = 32000（大三元）+ **300（本场棒）** + 8000，就是这条的直接证据。

⚠️ **最容易靠直觉写错的地方：每笔支付分别向上取整到百位，不是先求和再取整。**

[实现指南](实现指南.md) §1.8 给的例子：

```
子家 30 符 4 翻 自摸，基本点 1920
正确：子家 1920→2000，庄家 3840→3900   →  2000 / 2000 / 3900
错误：先求和 1920×4 = 7680 → 7700      →  差 200 点
```

**满贯封顶在基本点这一层做** —— 先算 `符 × 2^(2+翻)`，超过 2000 就按满贯表取值，然后再按支付规则换算。

**切上满贯是 M-League 的规定**（**【M】** 第 6 章第 4 条 2）—— 只影响 `30 符 4 翻` 与 `60 符 3 翻` 两个临界值（严格算 7700，切上后 8000）。**它不是可调开关**，`Rules.KiriageMangan` 存在只是为了标记"我们用了这条"。

**⚠️ 不要为「場ゾロ」加开关。** M-League 计算时恒加 2 翻，但那不改变任何赔付（[规则集](规则集.md) §0.1）。加开关只会给人机会把「含场ゾロ」的翻数传进来——那是 **4 倍误差**级别的 bug。

**⚠️ 帕奥（包）的三种付法各不相同**，见 [规则集](规则集.md) §8.5：

| 情形 | 谁付帕奥这一份 |
| --- | --- |
| 自摸 | **责任者一人独付全额**，另两家完全不付这一份 |
| 责任者放铳 | 责任者一人独付全额 |
| 别人放铳 | 责任者与放铳者**各付一半** |

**帕奥那一份要先剥出来** —— 实现上的顺序是：先按 `Yakuman − PaoYakuman` 算「不含帕奥的部分」并按常规分摊，再把帕奥那一份单独记到责任者头上。本场棒与立直棒**不参与帕奥分摊**，照常结算。

⚠️ **`Han` 必须是不含場ゾロ的实翻**，且 **役满时 `Han`/`Fu` 全部作废**。

### 6.4 `dora.go`

#### `func DoraFromIndicator(indicator Tile) Tile` ✅

**做什么** —— 返回一张指示牌所指示的宝牌。

⚠️ **字牌有两段独立的循环，一个取模走不完**：

```
风牌   东→南→西→北→东   （编号 27..30）
三元牌 白→发→中→白       （编号 31..33）
```

记法上的 `4z`（北）后面是 `1z`（东），但 `30+1` 会落到 31（白）——**这正是最容易写成 `(t+1) % NumTileKinds` 然后错掉的地方**。数牌段则是同花色内 1..9 循环（九万 → 一万）。

#### `func CountDora(tiles []Tile, indicators []Tile) int` ✅

**做什么** —— 数出 `tiles` 里有多少张由 `indicators` 指示的宝牌。

⚠️ **指示牌列表不能去重。** 两张相同的指示牌意味着**宝牌翻倍**，所以要按重数计——实现上用 `[NumTileKinds]int` 计数器而不是布尔表。

**杠按实际张数计**（`Meld.TilesUsed()` 已经处理了「杠用 4 张」）。

**里宝牌用同一个函数**，只是把 indicators 换成里宝牌指示牌——**并且只在立直和牌时才调用**（里宝牌不立直不翻开）。

#### `func AllTiles(concealed []Tile, melds []Meld) []Tile` ✅

**做什么** —— 返回一次和牌用到的**全部牌**：暗牌（含和牌张）+ 副露。

**为什么需要它** —— 数宝牌必须用全部牌，副露里的宝牌同样计数。写成「只看手牌」会漏掉副露里的，而**那种错误只在有人鸣牌时才出现**。

⚠️ **`concealed` 必须传原始牌，不能传 `Decomposition.Tiles()`。**
`Decomposition` 是从 `Counts` 建出来的（[`CountTiles`](#func-counttiles-counts-error) 已经把赤牌归一），
所以拿它来数赤宝牌会**一张都数不到**——而且不报错，赤宝牌翻数恒为 0。

这个签名**故意不给 `Decomposition` 留位置**，就是为了让那个错误写不出来。
有一条测试专门锁住这个事实（`TestDecompositionLosesAka`）。

#### 宝牌在流程里的位置 ⚠️

**宝牌不是役。** 它不参与「能不能和牌」的判定，只在这一步加翻数：

```
⑤ DetectYaku   → 役翻数
⑥ CountDora    → + 宝牌 + 里宝 + 赤宝      ← 就是这里
⑦ CalcFu
⑧ BasePoints / CalcScore
```

所以它必须发生在 `DetectYaku` **之后**、`CalcScore` **之前**。放错位置会做出「只有宝牌也能和牌」的游戏。

**役满时跳过第 ⑥ 步** —— 役满不看翻数，数了也没用。

⚠️ **还没有一个把这些步骤串起来的入口函数。** 现在 `CountDora` 是零件，谁来按顺序调它、谁来在役满时跳过，还没有着落。

## 7. `verify.go` —— 牌山可验证性 ✅

> 完整协议见 [牌山可验证性](牌山可验证性.md)。这三个函数让"服务器没作弊"从承诺变成可验证的事实。
>
> ⚠️ **这不是独门绝技**：雀魂（局中显示牌山哈希、赛后用「牌山代码+盐」重算）、天鳳
> （公开伪代码 + SHA512 哈希列表 + 全量日志）、Maru-Jan（2025-12 发布「无牌操作证明」）
> 都已有同类机制。本项目做的是**对齐行业标准**，差别只在把契约写成了可逐字节复算的字节表。
>
> ⚠️ **这一节的核心不是三个函数，是 §3.1 那张字节表。** 哈希输入是一串没有结构的字节，
> 每个字段的宽度就是契约本身。第三方照文档复算时差一个字节，就会算出不同的牌山，
> **然后误判服务器作弊**——这是这个功能最坏的失效方式。测试里的期望值因此是
> **照字节表独立重算**的，不是调实现比对实现。

#### `func Commit(gameID int64, serverSeed [32]byte) [32]byte` ✅

**做什么** —— 返回承诺值 `SHA256(域分隔串 ‖ gameID ‖ serverSeed)`。**开赛前公布它**，牌局结束后再公布 `serverSeed`。

哈希输入 = 域分隔串(17) ‖ `gameID`(8, big-endian) ‖ `serverSeed`(32)，共 **57 字节**。

**为什么这样能防作弊** —— 承诺值先公布，等于把服务器"锁死"在一个种子上：`SHA256` 不可逆，所以公布了承诺也推不出种子；但牌局结束后公布种子，任何人都能验证 `SHA256(域分隔串 ‖ gameID ‖ 种子)` 确实等于当初那个承诺——**服务器没可能在赛后换一个对自己有利的种子**。

**为什么必须混进 `gameID`** —— 否则同一个种子在不同牌局会产生同一个承诺，承诺就不再绑定具体牌局。

⚠️ **承诺必须先于牌局入库**，不能等结束一起写——**事后补写的承诺等于没有承诺**。数据库上有 3 条 `COMMENT` 专门强调这件事。

#### `func DeriveSeed(gameID int64, roundIndex int, serverSeed [32]byte, clientSeeds [4][32]byte) [32]byte` ✅

**做什么** —— 把服务器种子与四位玩家的种子混合成**最终种子**，用它洗牌。

哈希输入 = 域分隔串(17) ‖ `gameID`(8) ‖ `roundIndex`(**8**, big-endian) ‖ `serverSeed`(32) ‖ 四个 `clientSeed`(32×4)，共 **193 字节**。

**为什么要混玩家种子** —— 否则玩家只能验证"服务器没在赛后改种子"，但**服务器仍然能在赛前挑一个对自己有利的种子**。混入玩家各自提供的种子后，服务器在生成牌山时**还不知道**玩家的种子，所以无法定向操纵。

**四个参数缺一不可**：

| 参数 | 漏了会怎样 |
| --- | --- |
| `gameID` | 同一副牌山会在不同牌局重复出现 |
| `roundIndex` | 同一副牌山会在同一局的各小局重复出现 |
| `serverSeed` | 玩家能完全决定牌山 |
| `clientSeeds` | 服务器能完全决定牌山 |

⚠️ **`clientSeeds` 必须按座位顺序处理，不能当集合**。当成集合的话，交换两个人的种子结果不变——那就失去了"每个玩家都参与"的意义。

⚠️ **`roundIndex` 必须是 8 字节，不能用 `byte()`**。只留最低 8 位的话，`0` / `256` / `512` 会派生出**完全相同**的种子——同一个承诺下两小局的牌山一样，验证直接失效。测试里专门钉了这条。

⚠️ **玩家种子必须在洗牌前收齐**。文档 §10 明确列了这条局限：如果收得太晚，就没有意义了。

#### `func WallHash(w *Wall) [32]byte` ✅

**做什么** —— 牌山指纹 `SHA256(w.Bytes())`。

**它和 `Commit` 的分工** —— `Commit` 证明**种子没被换过**；`WallHash` 证明**从种子到牌山的洗牌过程没被换过**。两个都要通过，才算验证成功。

**为什么输入是 `w.Bytes()` 而不是 `w.Sequence()`** —— 两者都保持顺序，`Bytes()` 更直接（136 字节原始值，无需解析）。**但绝对不能用 `FormatTiles`**——它丢顺序。

#### 关于域分隔串

常量名 `wallDomain`，值是 `"majspirit/wall/v1"`（ASCII，**17 字节**），定义在 `internal/mahjong/verify.go`。

**为什么要有它** —— 把本协议的哈希和程序里其他地方（比如 JWT、会话）的哈希**隔开**，避免跨协议攻击。将来升级成 `v2` 也不会和旧记录混淆。

⚠️ **改这个串等于改协议版本。** 它出现在字节表的第一行，任何改动都必须同步 [牌山可验证性](牌山可验证性.md) §3.1 与 §3.3——否则第三方照文档复算会得到不同结果。

**验收方式** —— 改动域分隔串后**所有历史验证都会失败**，这就证明它确实在起作用。`verify_test.go` 里把它的长度钉成了 17 字节。

#### 这一节的测试

`internal/mahjong/verify_test.go`。关键的三条：

| 测试 | 抓什么 |
| --- | --- |
| `TestWallVerifyMatchesDocumentedFormula` | **实现偏离文档公式** —— 多套一层哈希、少写域分隔串、字段宽度不对 |
| `TestWallVerifyRoundIndexIsNotTruncated` | `roundIndex` 被截断（0 / 256 / 512 撞车） |
| `TestWallVerifyReplayReproducesWall` | 端到端模拟玩家第 9 节的第 4 步 |

> **为什么期望值要独立算**：这个文件里另有一套照字节表写的 `specCommit` / `specDeriveSeed`，
> 不复用 `verify.go` 的任何辅助函数。调实现去比对实现是同义反复——
> **上面那三种错它一个都抓不到。**

想先让包编译通过、留待后填，给每个函数一个会 panic 的体（写法见 §5）。

## 9. 赤宝牌是怎么落地的（已解决）

这一节保留下来，是因为**当时的建议是错的**，而错的理由值得记住。

### 曾经的选项

文档一度建议：「先把 `0m` 归一到 `5m`、丢弃赤属性让全链路跑通，等 `score.go`
要算赤宝牌时再补物理牌层」。**没有走这条路**，因为它有个真实的洞：

> `WallHash = SHA256(Wall.Bytes())`，而 `Bytes()` 是逐张 `byte(t)`。
> 归一之后赤五和普通五**字节相同**，于是两副只在"哪张五万是红的"上不同的牌山
> **哈希完全相同**。

后果很具体：承诺值公布之后、种子公布之前，服务器仍然可以自由决定赤五落在谁手里。
**那正是可验证牌山存在的意义。** 同一个问题还有第二个症状：`Wall.Sequence()` 的
注释写着「输出可被 `ParseTiles` 原样读回」，归一之后这句话直接是假的。

### 实际采用的方案

**给 `Tile` 加 3 个编号**（34/35/36 = 赤五万/赤五索/赤五筒），`NumTileKinds` 仍是 34，
另加 `Tile.Kind()` 把它们归一到普通五。

| 位置 | 改动 |
| --- | --- |
| `tile.go` | `Valid` 用 `NumTileCodes`(37)；`Suit`/`Rank`/`IsNumber`/`IsHonor` 先过 `Kind()`；`FullSet` 每种花色的五替换一张成赤牌（总数仍 136） |
| `parse.go` | `NewTile(suit, 0)` 构造赤五；`FormatTiles` 输出 `0` 并按 `Kind()` 排序 |
| `wall.go` | `Sequence()` 赤五写 `0`；`Bytes()` 的赤牌字节不同，**指纹因此绑住赤五位置** |
| `win.go` | `CountTiles` 用 `counts[t.Kind()]`，`>4` 判在归一之后 |
| `hand.go` | `Counts()`/`Count()`/`Tiles()` 按 `Kind()`；`Remove()` 保持**精确匹配** |
| `dora.go` | `DoraFromIndicator` 先归一（指示牌也可能是赤牌）；`CountDora` 走 `Kind()`；新增 `CountAka` |
| `yaku.go` / `fu.go` | 入口调 `ctx.normalized()` |
| `score.go` | 未改——`ScoreInput.Han` 由调用方把 `CountDora + CountAka` 加进去 |

**为什么不是 `PhysicalTile{Kind, Red}` 平行类型** —— `ParseTiles`/`FormatTiles`/
`Wall.Sequence`/协议牌字段/DB 每个边界都要转换一次，**每一次都是一次静默丢标记的机会**。
多 3 个编号则让 `"0m"` → `Tile(34)` → `FormatTiles` → `"0m"` 这套往返免费成立。

### 三处必须记住的约定

1. **`Counts` 的长度不能变成 37。** 赤五万一旦分到独立的桶，手里有赤五万就拆不出顺子，
   而且「4 张普通五 + 1 张赤五」会被放过去。归一化卡在 `CountTiles` 与 `Hand.Counts` 两处。
2. **`YakuContext.WinningTile` 与 `Melds` 不经过 `Counts`**，所以在 `DetectYaku`/`CalcFu`
   入口各调一次 `ctx.normalized()`。`YakuContext` 是按值传递的，归一改不到调用方——
   调用方仍然拿得到赤牌信息去数赤宝牌。
3. **`AllTiles` 收原始牌，不收 `Decomposition`。** `Decomposition.Tiles()` 是从 `Counts`
   建出来的，里面**永远数不到赤宝牌**。

⚠️ **第 2 条漏掉的症状是静默的**：荣和赤五万补成的刻子会被算成暗刻（少 2 符，
还让三暗刻错误成立），嵌张的 +2 会丢。所以在 `dora_test.go` 里专门留了一条
`TestCalcFuWithAkaWinningTileEmbedWait`——它挑的是**30 符 vs 40 符**这种跨过取整边界的
组合，而不是会被取整吃掉的 +2 符。
