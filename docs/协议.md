# MajSpirit 通信协议

> 本文是前端与服务端之间**唯一的接口契约**。任何一端改动本文描述的字段名、消息名或时序，必须同时改本文；只改代码不改本文，视为 bug。
>
> 状态：**草案 v0.1**（2026-10-03）。第 9 节列出的未决项尚未拍板，实现前需要先解决。
>
> 相关文档：[实现指南](实现指南.md)（§3.2 协议总则、§3.3 调试客户端）、[牌山可验证性](牌山可验证性.md)（§9 玩家验证流程）、[规则集](规则集.md)。

## 0. 本文的边界

**覆盖**：HTTP 接口、WebSocket 握手与生命周期、全部指令与事件的线格式、隐藏信息契约、一局的完整时序。

**不覆盖**：服务端内部实现（房间层 actor 模型、规则引擎）、数据库表结构、前端渲染方式。

## 1. 总则

以下五条不可协商。任何具体设计与之冲突时，改设计，不改总则。

### 1.1 服务端是唯一真源

客户端**不维护自己的游戏状态机**。所有状态变化由服务端推送，客户端只负责渲染收到的状态。

推论：客户端不做乐观预演。你打出一张牌，要等服务端确认才落到牌河。麻将的回合是严格串行的，本地先显示会让「出牌被抢杠」「出牌后被荣和」这类时序出现视觉上不可能的状态。

### 1.2 隐藏信息在服务端裁剪

别家的手牌**根本不出现在下发的 JSON 里**，不是「下发了但不显示」。

这条一旦破，前端怎么小心都没用——打开 DevTools 就看见所有人的牌。

具体契约见第 7 节。**任何新增消息都必须先回答「这条消息里有没有别家手牌」**。

### 1.3 牌一律用紧凑记法

牌以字符串传输，形如 `"123m456s789p11z"`，不展开成对象数组。

理由有三：① 数据库里就是这个形状（`game_walls.tiles`、`game_initial_hands.tiles` 都是 `TEXT`）；② **验牌页本来就必须自己解析紧凑记法**（要和 `game_walls.tiles` 逐张比对），所以前端的解析器是白送的，不是额外成本；③ 紧凑记法在日志、URL、复制粘贴里都能读。

记法定义见 §2.2。

### 1.4 每个事件带单调序号

服务端 → 客户端的每条事件都带 `seq`，同一房间内单调递增，从 1 开始。

客户端用它检测丢消息和重连定位。**`seq` 有洞就是丢了消息**，客户端应主动请求重新同步（§4.5）。

### 1.5 协议有版本号

服务端在 `hello` 里宣告 `protocolVersion`。客户端发现不认识的版本时，提示用户刷新，而不是带着错误假设继续跑。

## 2. 通用约定

### 2.1 编码与传输

| 项 | 约定 |
| --- | --- |
| HTTP | HTTP/1.1，开发期 `http://localhost:5173` 由 Vite 代理到 Go |
| WebSocket | 同源，路径 `/ws`；开发期同样走 Vite 代理 |
| 字符编码 | UTF-8 |
| 消息体 | JSON，`Content-Type: application/json; charset=utf-8` |
| 字段命名 | `camelCase`（Go 侧用 struct tag 导出，不靠默认行为） |
| 未知字段 | 接收方**必须忽略**，不得报错。这是为了能加字段而不升版本 |

### 2.2 牌与记法

**编码**：34 种牌，`0..33`。

| 区段 | 含义 |
| --- | --- |
| 0–8 | 一万 … 九万 |
| 9–17 | 一索 … 九索 |
| 18–26 | 一筒 … 九筒 |
| 27–30 | 东 南 西 北 |
| 31–33 | 白 发 中 |

**紧凑记法**：数字后跟花色字母，可分组书写。

| 字母 | 花色 | 示例 |
| --- | --- | --- |
| `m` | 万 | `123m` = 一万二万三万 |
| `s` | 索 | `789s` = 七索八索九索 |
| `p` | 筒 | `55p` = 五筒五筒 |
| `z` | 字牌 | `1z`=东 `2z`=南 `3z`=西 `4z`=北 `5z`=白 `6z`=发 `7z`=中 |

- 分组的**书写顺序无意义**：`"123m456s"` 与 `"456s123m"` 等价。
- **组内顺序有意义**：代表牌的物理排列，前端按此顺序渲染。
- **红宝牌**：数字 `0` 表示该花色的赤五，即 `0m` / `0s` / `0p`。例：`"055m"` = 红五万、五万、五万。
- **`0m` 与 `5m` 种类相同**。赤属性是叠加在种类之上的独立维度；和牌判定、役种、符数只看种类，只有宝牌计数区分。
- **牌背永不出现在协议里**。别家手牌根本不传（§1.2）。
- 字牌**不写数字以外的形式**（没有 `E`/`S`/`W`/`N` 别名）。

**术语**：本文与全项目统一用 **索 / 筒 / 白·发·中**（对应任务书的「条 / 饼 / 白板·发财·红中」）。

### 2.3 标识符

| 名称 | 类型 | 说明 |
| --- | --- | --- |
| `userId` | number | 用户 ID |
| `roomId` | string | 房间号，6 位大写字母数字，易念易输 |
| `gameId` | number | 一局（东南战整场）的 ID，对应 `games.id` |
| `roundIndex` | number | 第几局，从 1 开始，对应 `game_rounds.round_index` |
| `seat` | number | 座位 `0..3`。**`0` 是起家**，不是「自家」；自家座位由 `room.joined` 的 `mySeat` 给出 |
| `seq` | number | 事件序号，见 §1.4 |

**座位与风的关系**：`seat` 是固定的物理座位，**不随局数轮转**。自风 = `(seat - dealerSeat + 4) % 4` 映射到东南西北。这样前端不需要每局重排四个玩家的位置。

### 2.4 时间

- 所有时间戳是**毫秒整数**（Unix epoch），字段名以 `At` 结尾，如 `startedAt`。
- 所有时长是**毫秒整数**，字段名以 `Ms` 结尾，如 `deadlineMs`。
- 服务端时间与客户端时间可能有偏差；**倒计时一律用服务端给的 `deadlineMs`（绝对时间戳）配合 `serverTime` 校准**，不要用本地 `Date.now()` 直接算。

### 2.5 鉴权

- HTTP：`Authorization: Bearer <token>`。
- WebSocket：**见 §4.1**，浏览器 `WebSocket` API 无法设置请求头，所以不走同一套。

### 2.6 错误码

错误码是**稳定的机器可读标识**，`message` 才是给人看的。

| 码 | 含义 |
| --- | --- |
| `BAD_REQUEST` | 消息结构或字段类型不对 |
| `UNKNOWN_COMMAND` | `type` 不认识 |
| `AUTH_REQUIRED` | 未认证就发了需要认证的指令 |
| `AUTH_FAILED` | token 无效或过期 |
| `RATE_LIMITED` | 请求过于频繁 |
| `NOT_IN_ROOM` | 不在任何房间 |
| `ALREADY_IN_ROOM` | 已在其它房间 |
| `ROOM_NOT_FOUND` | 房间号不存在 |
| `ROOM_FULL` | 房间已满四人 |
| `ROOM_STARTED` | 对局已开始，无法加入 |
| `NOT_ROOM_OWNER` | 只有房主能执行 |
| `NOT_YOUR_TURN` | 不是你的回合 |
| `ILLEGAL_ACTION` | 动作合法但当前不成立（如没听牌就立直） |
| `TILE_NOT_IN_HAND` | 打出的牌不在手里 |
| `INTERNAL` | 服务端内部错误，细节不暴露 |

## 3. HTTP 接口

用于**对局之外**的事务：账号、历史、验证。对局过程一律走 WebSocket。

### 3.1 `POST /api/register`

创建账号。无需鉴权。

```jsonc
// 请求
{ "username": "aleksey", "password": "……" }

// 201
{ "userId": 42, "username": "aleksey", "createdAt": 1759459200000 }
```

| 错误 | 码 |
| --- | --- |
| 用户名已占用 | `409 USERNAME_TAKEN` |
| 用户名或密码不合法 | `400 BAD_REQUEST` |

用户名唯一性是大小写不敏感的（数据库上有 `lower(username)` 唯一索引）。

### 3.2 `POST /api/login`

```jsonc
// 请求
{ "username": "aleksey", "password": "……" }

// 200
{
  "token": "……",
  "expiresAt": 1759545600000,
  "user": { "userId": 42, "username": "aleksey" }
}
```

| 错误 | 码 |
| --- | --- |
| 用户名或密码错误 | `401 AUTH_FAILED`（**不区分**是哪一个错，避免账号枚举） |

### 3.3 `POST /api/logout`

需要鉴权。使当前 token 失效。

```
204 No Content
```

### 3.4 `GET /api/me`

需要鉴权。前端启动时用它校验本地 token 是否还有效。

```jsonc
// 200
{ "userId": 42, "username": "aleksey", "createdAt": 1759459200000 }
```

### 3.5 `GET /api/history`

需要鉴权。返回当前用户参与过的牌局，按时间倒序。

```jsonc
// 200
{
  "games": [
    {
      "gameId": 1001,
      "startedAt": 1759459200000,
      "finishedAt": 1759462800000,
      "seat": 2,
      "placement": 1,
      "initialScore": 25000,
      "finalScore": 41200,
      "points": 61200
    }
  ],
  "nextCursor": null
}
```

`placement` 为 `1..4` 表示名次；`nextCursor` 非空时表示还有更多，传 `?cursor=<值>` 取下一页。

### 3.6 `GET /api/games/{gameId}`

需要鉴权。返回一局的可读存档，**用于复盘**。

```jsonc
// 200
{
  "gameId": 1001,
  "startedAt": 1759459200000,
  "finishedAt": 1759462800000,
  "rules": { /* 规则快照，见算分文档 §14 */ },
  "seats": [
    { "seat": 0, "userId": 42, "username": "aleksey", "initialScore": 25000, "finalScore": 41200, "placement": 1, "points": 61200 }
  ],
  "rounds": [
    {
      "roundIndex": 1,
      "roundWind": "1z",
      "handNumber": 0,
      "dealerSeat": 0,
      "endedBy": "win",
      "winnerSeat": 2,
      "isTsumo": false,
      "winningTile": "5p",
      "riichiSticks": 1,
      "initialHands": ["123m456s789p11z", "……", "……", "……"],
      "doraIndicators": ["3s"],
      "uraIndicators": ["7m"],
      "events": [
        { "seq": 1, "seat": 0, "action": "draw",    "tile": "9m", "detail": null },
        { "seq": 2, "seat": 0, "action": "discard", "tile": "9m", "detail": { "tsumogiri": true } }
      ],
      "wins": [
        {
          "winSeq": 1,
          "winnerSeat": 2,
          "loserSeat": 0,
          "isTsumo": false,
          "winningTile": "5p",
          "han": 3,
          "fu": 40,
          "yakuman": 0,
          "yaku": [{ "name": "立直", "han": 1 }, { "name": "平和", "han": 1 }],
          "dora": { "dora": 1, "ura": 1, "aka": 0 },
          "payments": { "0": -3900, "1": 0, "2": 3900, "3": 0 }
        }
      ]
    }
  ]
}
```

**隐藏信息规则**：只有 `finishedAt` 非空（对局已结束）时，`initialHands` 和完整 `events` 才下发。**对局进行中调用本接口，别家手牌相关字段一律为 `null`**。复盘页必须处理这个情况。

### 3.7 `GET /api/games/{gameId}/verify`

需要鉴权。返回**牌山独立验证所需的全部原始数据**。

```jsonc
// 200
{
  "gameId": 1001,
  "roundIndex": 1,
  "goVersion": "go1.27.0",
  "domain": "majspirit/wall/v1",
  "serverSeed": "6f1a…",          // hex，32 字节
  "clientSeeds": ["…", "…", "…", "…"], // hex，按 seat 0..3 顺序，可能含 null
  "commitment": "a3c9…",          // hex，32 字节
  "wallHash": "10b5…",            // hex，32 字节
  "tiles": "1m5p3s2z…",           // 按摸牌顺序 136 组紧凑记法
  "doraIndicators": ["3s"],
  "uraIndicators": ["7m"],
  "committedAt": 1759459100000
}
```

**注意**：`tiles` 是**按摸牌顺序**的逐张序列（对应 Go 的 `Wall.Sequence()`），不是分组排序后的形状（**不是** `FormatTiles`）。顺序就是全部信息，用分组记法验证必然失败。

**也注意**：`tiles` 在这里**必须下发**，哪怕是进行中的对局——因为承诺已经上链（`committedAt` 早于开局），下发完整牌山不会让任何人作弊，只会让作弊**可被发现**。这是设计的一部分，不是漏洞。前端验牌页要做的事见 [牌山可验证性](牌山可验证性.md) §9。

## 4. WebSocket

### 4.1 端点与握手

**端点**：`/ws`

**为什么鉴权不走 `Authorization` 头**：浏览器原生 `WebSocket` 构造函数**无法设置请求头**。可选方案只有三个：

| 方案 | 问题 |
| --- | --- |
| `?token=…` 查询串 | token 会进服务器访问日志、浏览器历史、代理日志 |
| 子协议 `new WebSocket(url, ['majspirit.v1', token])` | 能用，但把凭据塞进协议协商字段，语义错位 |
| **首条消息 `auth`** | **采用** |

**时序**：

```
客户端连接 /ws
服务端 → 客户端   hello        { protocolVersion, serverTime, sessionId }
客户端 → 服务端   auth         { token }
服务端 → 客户端   authed       { userId, username }       或  error{AUTH_FAILED} + 关闭
```

**规则**：

- 收到 `authed` 之前，服务端拒绝其它一切指令，回 `error{AUTH_REQUIRED}`。
- 连接后 **5 秒**内未收到 `auth`，服务端以关闭码 `4401` 关闭。
- `auth` 失败后服务端**直接关闭**，不允许重试（防止暴力破解）。重新连接再试。

### 4.2 信封

两个方向统一：

```jsonc
{ "type": "<命令名或事件名>", "data": { /* ... */ } }
```

- `type` 是**字符串**，不是数字枚举（可读、可扩展、日志里能直接看懂）。
- 客户端 → 服务端叫**指令**，服务端 → 客户端叫**事件**。
- 每种 `type` 有独立的 Go 结构体，**不用一个万能 struct**。
- `data` 可以为 `{}`，但**不可省略**。

事件额外带一个 `seq`：

```jsonc
{ "type": "game.discard", "seq": 17, "data": { "seat": 2, "tile": "5p", "tsumogiri": false } }
```

（`seq` 放在信封层而不是 `data` 里，因为它是传输属性，不是业务字段。）

### 4.3 心跳

- 服务端每 **15 秒**发 `ping`，客户端须在 **5 秒**内回 `pong`。
- 客户端可以主动发 `ping`，服务端回 `pong`。
- 连续两次未回 `pong`，服务端判定连接已死，以关闭码 `4408` 关闭。

### 4.4 序号与丢消息

客户端记录每个房间收到的最大 `seq`。新事件的 `seq` **不等于** `max+1` 时：

1. 说明丢消息（网络抖动、服务端 bug 都可能）。
2. 客户端**不得**尝试猜测缺失内容，直接发 `game.sync` 指令请求全量快照。

### 4.5 重连

断线重连的完整流程：

```
客户端重新连接 /ws
客户端 → 服务端   auth { token }
服务端 → 客户端   authed { … }
客户端 → 服务端   game.sync {}          // 若重连前在对局中
服务端 → 客户端   game.snapshot { … }   // 全量可见状态，见 §6.2
```

`game.snapshot` 之后事件流从新的 `seq` 继续。**前端不需要为「重连」写特殊逻辑**——它和首次进入牌桌走的是同一条路径，都是「拿一份快照，之后消费事件」。

服务端为断线玩家保留座位 **60 秒**。超时视为退出，广播 `room.seatVacated`。

### 4.6 关闭码

| 码 | 含义 |
| --- | --- |
| `1000` | 正常关闭 |
| `4400` | 协议错误（无法解析的消息、非法 JSON） |
| `4401` | 未认证 / 认证失败 |
| `4403` | 被服务端拒绝（如在别处登录） |
| `4408` | 心跳超时 |
| `1011` | 服务端内部错误 |

## 5. 指令（客户端 → 服务端）

### 5.1 会话

| `type` | `data` | 说明 |
| --- | --- | --- |
| `auth` | `{ token }` | 见 §4.1 |
| `ping` | `{}` | 心跳 |

### 5.2 房间

| `type` | `data` | 说明 |
| --- | --- | --- |
| `room.create` | `{}` | 创建房间，成为房主，占 `seat 0` |
| `room.join` | `{ roomId }` | 加入房间；成功占最小空位 |
| `room.leave` | `{}` | 离开房间（对局中视为认输/退出） |
| `room.ready` | `{ ready: boolean }` | 准备状态；四人全 ready 且房主开局 |
| `room.start` | `{}` | **仅房主**，四人齐且全 ready 时开局 |

### 5.3 对局

所有对局指令都要求「轮到你能做这个动作」，否则回 `error{ILLEGAL_ACTION}`。

| `type` | `data` | 说明 |
| --- | --- | --- |
| `game.sync` | `{}` | 请求全量快照（重连、或检测到 `seq` 有洞时） |
| `game.discard` | `{ tile }` | 打出一张牌。`tile` 是紧凑记法单张，如 `"5p"`、`"0s"` |
| `game.riichi` | `{ tile }` | **立直宣言同时打牌**，合并为一条指令，避免「宣言了但没打出去」的中间态 |
| `game.chi` | `{ tiles: ["3s","4s"] }` | 吃。只给出手里要用的两张，被吃的那张由服务端从牌河推出 |
| `game.pon` | `{}` | 碰。牌由服务端从牌河推出 |
| `game.kan` | `{ kind, tile? }` | `kind` ∈ `open` / `closed` / `added`。`closed` 和 `added` 需要 `tile`，`open` 不需要 |
| `game.win` | `{}` | 荣和或自摸（服务端按上下文判断是哪种） |
| `game.pass` | `{}` | 过。用于放弃鸣牌/和牌机会 |

**没有"流局宣言"类指令。** M-League 不采用任何途中流局，所以**不存在** `game.kyuushu`
（九种九牌）或 `game.agree_draw`（途中流局同意）——一局只能以**和牌**或**荒牌流局**结束，
两者都由服务端自动判定，不需要玩家宣告。见 [规则集](规则集.md) §11.2。

**关于 `game.pass`**：只要当前存在可鸣牌/可和牌的机会，服务端就会开一个**鸣牌窗口**（§6.6）。窗口内的玩家必须显式回 `game.chi`/`game.pon`/`game.kan`/`game.win` 或 `game.pass`。**不回视为放弃**（超时，§6.6）。

**关于食替**：M-League 把食替判为**「和牌放弃」（アガリ放棄）**——**牌可以打出去，服务端接受这个动作**，但该玩家此后**不能再和牌**（**【M】** 第 7 章第 2 条 2(3)）。

> ⚠️ 这与"拒绝动作"**不同**：不要回 `ILLEGAL_ACTION`，而是记一个座位级的「和牌放弃」标志。食替的判定需要房间层记住"刚鸣的那一组牌"，不能只看手牌。

## 6. 事件（服务端 → 客户端）

### 6.0 事件总览

| 分组 | 事件 |
| --- | --- |
| 连接 | `hello` `authed` `ping` `pong` `error` |
| 房间 | `room.created` `room.joined` `room.seats` `room.readyChanged` `room.left` `room.seatVacated` |

### 6.1 连接

```jsonc
// hello —— 连上后服务端的第一条
{ "type": "hello", "data": {
    "protocolVersion": 1,
    "serverTime": 1759459200000,
    "sessionId": "…"
} }

// authed
{ "type": "authed", "data": { "userId": 42, "username": "aleksey" } }

// ping / pong
{ "type": "ping", "data": { "serverTime": 1759459200000 } }
{ "type": "pong", "data": { "serverTime": 1759459200000 } }

// error —— 任何指令失败
{ "type": "error", "data": {
    "code": "ROOM_NOT_FOUND",
    "message": "房间不存在",
    "ref": "room.join"        // 触发它的指令名，便于前端定位
} }
```

### 6.2 房间

```jsonc
// room.created
{ "type": "room.created", "data": { "roomId": "7KQ2ZP", "seat": 0 } }

// room.joined —— 只发给加入者，带自己的座位
{ "type": "room.joined", "data": {
    "roomId": "7KQ2ZP",
    "mySeat": 2,
    "seats": [ /* 见下方 seatState */ ]
} }

// room.seats —— 座位有变化时广播给全房间
{ "type": "room.seats", "data": { "seats": [ /* seatState[] */ ] } }

// seatState
{ "seat": 0, "userId": 42, "username": "aleksey", "ready": true, "connected": true, "isOwner": true }
```

`room.readyChanged` / `room.left` / `room.seatVacated` 同理，只带变化的那一项：

```jsonc
{ "type": "room.readyChanged", "data": { "seat": 2, "ready": true } }
{ "type": "room.left",         "data": { "seat": 2 } }
{ "type": "room.seatVacated",  "data": { "seat": 2, "reason": "timeout" } }
```

### 6.3 对局开始

`game.started` **每个座位收到的内容不同**——这是隐藏信息契约的第一个落点。

```jsonc
{ "type": "game.started", "data": {
    "gameId": 1001,
    "roundIndex": 1,
    "roundWind": "1z",          // 场风，紧凑记法单张
    "handNumber": 0,            // 本场
    "dealerSeat": 0,
    "mySeat": 2,
    "myHand": "123m456s789p11z",   // ★ 只有自家的 13 张
    "scores": [25000, 25000, 25000, 25000],
    "riichiSticks": 0,
    "remaining": 84,            // 牌山剩余（发牌后，庄家尚未摸第 14 张）
    "doraIndicators": ["3s"],
    "firstTurn": 0              // 第一个行动的是庄家
} }
```

**注意 `remaining` 的语义**：发牌流程是四家各 13 张（共 52），剩 84。庄家的第 14 张是它自己的第一次摸牌，会作为一条 `game.drew` 事件发出，**不包含在 `game.started` 里**。

`game.snapshot`（重连/`game.sync` 用）是 `game.started` 的超集，额外带牌河、副露、当前手番等：

```jsonc
{ "type": "game.snapshot", "data": {
    /* game.started 的全部字段，加上： */
    "myHand": "…",
    "discards": [ ["9m","1p"], ["3s"], [], ["7z","5p"] ],   // 按 seat 索引
    "melds": [ [], [], [{ "kind": "pon", "tiles": "111z", "fromSeat": 0 }], [] ],
    "doraIndicators": ["3s"],
    "turn": { "seat": 1, "deadlineMs": 1759459220000 },
    "claim": null,              // 非空时见 §6.6
    "riichiSeats": [2],
    "ippatsuSeats": []
} }
```

### 6.4 摸打

```jsonc
// game.drew —— ★ 隐藏信息第二个落点
// 发给自己
{ "type": "game.drew", "seq": 33, "data": { "seat": 2, "tile": "5p", "remaining": 71 } }
// 发给别人（同一时刻，同一个 seq）
{ "type": "game.drew", "seq": 33, "data": { "seat": 2, "remaining": 71 } }
```

**`tile` 字段只出现在「摸牌者自己」收到的版本里。** 别家只知道「他摸了一张」，不知道是什么。

前端渲染依据：`tile` 存在 → 把牌插进自家手牌并播摸牌动画；`tile` 不存在 → 只播「对面摸牌」的表现（如手牌数 +1）。

```jsonc
// game.discarded —— 打出的牌所有人都看得见，无隐藏信息
{ "type": "game.discarded", "seq": 34, "data": {
    "seat": 2,
    "tile": "5p",
    "tsumogiri": false,     // true = 摸切
    "riichi": false,        // true = 这张是立直宣言牌，前端应横放
    "remaining": 71
} }

// game.turn —— 轮到谁，带绝对截止时间
{ "type": "game.turn", "seq": 35, "data": {
    "seat": 3,
    "deadlineMs": 1759459220000
} }
```

### 6.5 鸣牌

```jsonc
// game.meld —— 某人完成鸣牌，所有人都看得见
{ "type": "game.meld", "seq": 40, "data": {
    "seat": 1,
    "kind": "chi",              // chi / pon / openKan / closedKan / addedKan
    "tiles": "345s",            // 组成鸣牌的全部牌，紧凑记法
    "fromSeat": 2,              // 被鸣的那张来自谁；暗杠时等于 seat
    "calledTile": "5s",
    "remaining": 69
} }

// game.doraRevealed —— 新宝牌指示牌翻开（杠发生时，以及开局）
{ "type": "game.doraRevealed", "seq": 41, "data": {
    "indicator": "7m",
    "isUra": false,
    "kanCount": 1
} }
```

**宝牌指示牌是列表，不是单张。** 每次杠翻开一张新的，前端要追加而不是替换。指示牌**可能有重复**（两张 `3s` 指示牌意味着宝牌番数翻倍），前端不得去重。

**⚠️ 全场开杠上限 4 个。** M-League 不采用「四杠散了流局」，取而代之的是
「一局中の開槓数は全体で4つまで」——**第 5 个杠这个动作本身被拒绝**
（服务端回 `ILLEGAL_ACTION`），**牌局继续**，不是一个流局。所以 `kanCount` 只可能取 0–4。
见 [规则集](规则集.md) §11.2。

### 6.6 鸣牌窗口

**窗口有两个触发源**，服务端用同一个事件处理，靠 `trigger` 区分：

| `trigger` | 什么时候开 | 争的是哪张牌 | 可能的动作 |
| --- | --- | --- | --- |
| `discard` | 有人**打出一张牌** | 打牌者的舍牌 | 吃 / 碰 / 大明杠 / 荣和 |
| `addedKan` | 有人**宣言加杠**（抢杠） | 加杠的那张牌 | **只有荣和** |

窗口**只推给有资格的座位**：

```jsonc
// trigger: discard
{ "type": "game.claimWindow", "seq": 36, "data": {
    "trigger": "discard",
    "fromSeat": 2,                                     // 打牌者
    "tile": "5p",
    "options": ["chi", "pon", "kan", "ron", "pass"],   // ★ 只列这家真正能做的
    "deadlineMs": 1759459230000
} }

// trigger: addedKan（抢杠）
{ "type": "game.claimWindow", "seq": 47, "data": {
    "trigger": "addedKan",
    "fromSeat": 1,                                     // 加杠者
    "tile": "5s",
    "options": ["ron", "pass"],                        // 吃碰杠在此都不存在
    "deadlineMs": 1759459230000
} }
```

`options` 是**按座位裁剪**的：能荣和的人看到 `ron`，能吃的人看到 `chi`，都不能的人**根本收不到这条事件**。

> **加杠窗口还要按振听裁剪。** 处于振听的人**不该**收到 `ron`——振听的优先级高于和牌（见 [规则集](规则集.md) §2.2）。

窗口结束：

```jsonc
{ "type": "game.claimClosed", "seq": 37, "data": {
    "trigger": "discard",
    "resolvedBy": "pon",       // 没有任何人鸣则 null
    "seat": 1
} }
```

**多人同时鸣牌的优先级**（服务端裁决，前端只呈现结果）：**荣和 > 碰/杠 > 吃**。同级之间按**离触发者的逆时针顺序**（即下家优先）。

**一炮多响取头跳**：同一张牌有多家可荣和时，**只有最近的一家**（触发者的下家 → 对家 → 上家）能荣，其余视为自动 `pass`。因此**每局只承认一家和牌**，「三家和了流局」在本项目中不可达。

> 依据：M-League 与日本プロ麻雀连盟的竞赛规定措辞一致——「アガリ者は一局に 1 人とする」。
> 见 [规则集](规则集.md) §14。

**超时**：窗口内未回应的座位视为 `pass`。超时后服务端自行裁决并发 `game.claimClosed`。**前端不得自己判定窗口结束**——必须等 `game.claimClosed`。

#### 加杠的时序（抢杠的后果）

抢杠会**取消那个加杠**，所以事件顺序不是想当然的：

```
① 某人     → 服务端   game.kan { kind: "added", tile: "5s" }
② 服务端   → 有资格者 game.claimWindow { trigger: "addedKan", tile: "5s", options: ["ron","pass"] }

   分支 A：无人荣和
③ 服务端   → 全体    game.meld { kind: "addedKan", … }
④ 服务端   → 全体    game.doraRevealed { … }

   分支 B：有人荣和
③′ 服务端  → 全体    game.winDeclared { … }
④′ 服务端  → 全体    game.roundEnd { … }
   ★ 没有 game.meld，也没有 game.doraRevealed —— 杠不成立（见算分文档 §3.1）
```

**所以 `game.meld` 必须等窗口关闭之后才发**，不能在收到 `game.kan` 时就广播。这是抢杠在协议层唯一的复杂之处。

**⚠️ 暗杠没有窗口。** 本项目**禁止抢暗杠**（算分文档 §14），所以 `kind: "closed"` 直接产生 `game.meld` + `game.doraRevealed`，不经过第 ② 步。

**⚠️ 大明杠也没有额外窗口。** 大明杠吃的是别人刚打出的牌，那张牌的 `discard` 窗口里已经包含 `ron`——而且**荣和优先于大明杠**。所以 `kind: "open"` 走的是「弃牌窗口无人荣和 → 大明杠成立」这条既有路径，不需要新机制。

### 6.7 立直

```jsonc
{ "type": "game.riichi", "seq": 50, "data": {
    "seat": 2,
    "tile": "5p"          // 宣言牌，等同一条 game.discarded{riichi:true}
} }

// 立直成立（供托 +1000，且此后打出的牌不能再被鸣）
{ "type": "game.riichiStick", "seq": 51, "data": {
    "seat": 2,
    "sticks": 1,
    "scores": [25000, 25000, 24000, 25000]
} }

// 一发成立（立直后一巡内和牌）
{ "type": "game.ippatsu", "seq": 52, "data": { "seat": 2, "active": true } }
```

立直宣言和打牌是**同一条指令**（`game.riichi`），但服务端发**两条事件**：`game.riichi`（宣言，前端横放那张牌）和 `game.riichiStick`（供托扣除，前端更新分数）。分开是因为前者是牌桌上的视觉变化，后者是计分区变化。

### 6.8 和了与结算

```jsonc
// game.winDeclared —— 有人宣告和牌，先揭示，再算分
{ "type": "game.winDeclared", "seq": 60, "data": {
    "seat": 2,
    "isTsumo": false,
    "winningTile": "5p",
    "fromSeat": 0,
    "hand": "123m456s789p11z",   // ★ 只有和牌者的手牌在此刻揭示
    "melds": []
} }

// game.roundEnd —— 一局结束（和了或流局）
{ "type": "game.roundEnd", "seq": 61, "data": {
    "roundIndex": 1,
    "endedBy": "win",                 // win / draw —— 没有 abortive
    "wins": [ {                       // 一局只可能有 0 或 1 家
        "winnerSeat": 2,
        "loserSeat": 0,
        "isTsumo": false,
        "winningTile": "5p",
        "han": 3,
        "fu": 40,
        "yakuman": 0,
        "yaku": [ { "name": "立直", "han": 1 }, { "name": "平和", "han": 1 }, { "name": "断幺九", "han": 1 } ],
        "dora": { "dora": 1, "ura": 0, "aka": 0 },
        "paoSeat": null,              // ★ 帕奥责任者；无包时为 null（见下）
        "paoYaku": null,              // ★ 由哪个役满触发包，如 "大三元"
        "payments": { "0": -3900, "1": 0, "2": 3900, "3": 0 }
    } ],
    "hand": "123m456s789p11z",        // 和牌者手牌，供结算面板展示
    "deltas": [0, 0, 3900, 0],        // 本局四家分数变化
    "newScores": [21100, 25000, 28900, 25000],
    "riichiSticks": 1,                // 本局结束时台上的供托（归和牌者）
    "dealerRepeats": false,           // 是否连庄
    "uraIndicators": ["7m"]           // ★ 只有立直且和牌时才揭示
} }
```

**没有 `abortive`，也没有 `abortiveReason`。** M-League 不采用任何形态的途中流局
（九种九牌 ／ 四风连打 ／ 四家立直 ／ 四杠散了 ／ 三家和了 全都不成立），
所以 `endedBy` 只有两个取值。见 [规则集](规则集.md) §11.2。

**`wins` 数组的语义：一局只可能有 0 或 1 个元素。** M-League 采用头跳——一张牌多家可荣和时，
按**放铳者的下家 → 对家 → 上家**的顺序只有最近的一家能荣。保留数组形式只是为了将来
若换成允许双响的规则集时不用改结构。

**`paoSeat` / `paoYaku`：帕奥（包）。** M-League 有责任払い，适用于大三元、大四喜、四槓子
三种役满（[规则集](规则集.md) §8.5）。非 null 时，`payments` 里会出现**某一座独自承担
全额**的大额支出——前端展示时要能解释这个数字，别当成 bug：

```jsonc
// 一本场，西家让南家碰出大三元，南家手牌为大三元 + 字一色，南家自摸
"paoSeat": 1, "paoYaku": "大三元",
"payments": { "0": -16000, "1": -40300, "2": 64300, "3": -8000 }
```

**刻意没有 `sancha_hou`（三家和了）**——本项目采用头跳（§6.6），一局只承认一家和牌，该原因永远不可达。它也已从 `migrations/0001_init.sql` 的 CHECK 枚举中移除。

**流局（`endedBy: "draw"`）** 时 `wins` 为空数组，但额外带听牌信息：

```jsonc
{ "type": "game.roundEnd", "data": {
    "endedBy": "draw",
    "wins": [],
    "tenpaiSeats": [0, 2],
    "notenSeats": [1, 3],
    "tenpaiHands": [              // ★ 流局才揭示，且只揭示听牌家
        { "seat": 0, "hand": "…", "waiting": ["3s","6s"] },
        { "seat": 2, "hand": "…", "waiting": ["1p"] }
    ],
    "deltas": [1500, -1500, 1500, -1500],
    "newScores": [25000, 25000, 25000, 25000]
} }
```

**整场结束**：

```jsonc
{ "type": "game.gameEnd", "seq": 200, "data": {
    "gameId": 1001,
    "finalScores": [41200, 18900, 25100, 14800],
    "placements":  [1, 3, 2, 4],        // 按 seat 索引
    "points":      [61200, -14100, -15900, -31200],  // ★ 单位是「点」，见下
    "reason": "all_last_round"          // all_last_round / agreed —— 没有 bankrupt
} }
```

**`points` 是 M-League 的ポイント**（B 层大会规定，见 [规则集](规则集.md) §10.4）：

```
points[i] = (finalScores[i] − 30000) + 顺位点[placements[i]] × 1000
顺位点 = { 1位: +50, 2位: +10, 3位: −10, 4位: −30 }
```

**单位是「点」而不是「pt」**：上例的 `61200` 表示 `+61.2 pt`（1000 点 = 1 pt）。
用整数传输是为了避开浮点误差，前端除以 1000 再显示。

**`reason` 没有 `bankrupt`。** M-League **没有飞人**——即使有人被击飞到 0 点以下，
也要打完最终局（[规则集](规则集.md) §10.3）。所以整场结束只有两种原因。

## 7. 隐藏信息契约

**这是全文最重要的一节。** 任何新增消息都必须先在这里登记。

### 7.1 四类信息

| 类别 | 例子 | 谁能看到 |
| --- | --- | --- |
| **公开** | 牌河、副露、宝牌指示牌、分数、供托、剩余牌数、当前手番 | 所有人，广播 |
| **私有** | 自家手牌、摸到的牌 | **只有本人**，按座位裁剪下发 |
| **延迟公开** | 和牌者的手牌、流局时听牌家的手牌 | 揭示时刻之后，所有人 |
| **永不下发** | **别家手牌**（对局进行中）、牌山剩余的张是什么、里宝牌指示牌（未和牌时） | **任何人，任何时刻** |

### 7.2 逐条核对表

| 事件 | 公开部分 | 座位相关部分 | 绝不能出现 |
| --- | --- | --- | --- |
| `game.started` | scores、doraIndicators、remaining | `myHand` 只给本人 | 别家 13 张 |
| `game.snapshot` | discards、melds、turn | `myHand` 只给本人 | 别家 13 张 |
| `game.drew` | seat、remaining | `tile` 只给摸牌者 | 别家的 `tile` |
| `game.discarded` | 全部 | — | — |
| `game.claimWindow` | — | `options` 按座位裁剪 | 别家能不能鸣 |
| `game.winDeclared` | 全部（和牌者手牌此时揭示） | — | — |
| `game.roundEnd` | 和牌信息、分数变化 | `uraIndicators` 仅立直和牌时 | 未和牌家的手牌 |
| `game.roundEnd`（流局） | tenpaiSeats | `tenpaiHands` 只含听牌家 | **未听牌家的手牌** |
| `game.gameEnd` | 最终分数、名次 | — | — |

### 7.3 三个容易犯的错

1. **「前端不显示就行了」。** 不行。不下发才是唯一正确做法。前端代码是可以被阅读和修改的，`v-if="false"` 不是安全措施。
2. **在 `game.claimWindow` 里告诉所有人「谁在考虑鸣牌」。** 这是泄漏。某人收到 `options: ["ron"]` 这件事本身，就暴露了他可能有和牌机会。所以窗口事件**只推给有资格的座位**，而不是广播后各自过滤。
3. **`remaining` 泄漏牌山内容。** `remaining` 只是数量，是公开信息，没问题。但**不要**顺手把「牌山还剩哪些牌」也发下去——那等于公开所有人的听牌。

## 8. 一局的完整时序

```
       房主                   服务端                    玩家 A(2)
        │                       │                          │
        │  room.start           │                          │
        ├──────────────────────>│                          │
        │                       │  洗牌(commit-reveal)、发牌  │
        │                       │                          │
        │  game.started         │  game.started            │
        │<──────────────────────┼─────────────────────────>│  引擎: myHand 13 张
        │  (myHand = 自家13张)   │  (myHand = A 的13张)      │
        │                       │                          │
        │                       │  game.turn {seat:0}      │
        │<──────────────────────┼─────────────────────────>│
        │  game.drew {tile:"9m"}│  game.drew {}            │
        │<──────────────────────┼─────────────────────────>│  引擎: A 只看到"庄家摸牌"
        │                       │                          │
        │  game.discarded       │  game.discarded          │
        │  {seat:0,tile:"9m"}   │  {seat:0,tile:"9m"}      │
        │<──────────────────────┼─────────────────────────>│  引擎: 9m 进牌河
        │                       │                          │
        │                       │  game.claimWindow        │  ★ 只推给有资格的座位
        │                       ├─────────────────────────>│  options:["chi","pass"]
        │                       │                          │
        │  game.pass            │                          │
        │<──────────────────────┤                          │
        │                       │  game.claimClosed        │
        │<──────────────────────┼─────────────────────────>│
        │                       │                          │
        │                       │  game.turn {seat:1}      │
        │<──────────────────────┼─────────────────────────>│
```

**关键点**：`game.started` 是**逐座位定制**的，不同座位收到不同的 `data`。这不是可选的优化，而是 §1.2 的直接后果。

**第二个关键点**：客户端在任何时刻都不需要「推算」任何东西。它拿到什么就画什么。如果前端代码里出现了「因为 X 所以 Y 应该是……」的逻辑，那是设计出问题了。

## 9. 未决问题

以下是本文档尚未拍板的部分。**实现第 5、6 节之前必须先解决**。

### 9.1 操作超时的策略

§6.4 和 §6.6 分了两种超时（回合超时、鸣牌窗口超时），但**超时时长**没定，也没定是否可以配置。候选：回合 5 秒 + 读秒 3×10 秒，鸣牌窗口 3 秒。

### 9.2 观战

本协议**没有观战**。如果要做，§7 的契约要整体重审（观战者能看到什么？延迟？）。

### 9.3 `game.snapshot` 是否该在每次事件后都附一份

一个替代设计：**每条事件都携带完整的可见快照**。好处是前端完全不需要维护状态机、重连天然免费、调试时分外直观；代价是消息变大（但麻将一秒几次操作，几 KB 无所谓）。

当前设计走的是「事件流 + 按需快照」，因为它和 [实现指南](实现指南.md) §3.2 已定的「指令/事件」命名一致，而且事件语义是动画编排所需要的。

**但这一条值得重新考虑**，因为 §1.1「客户端不维护状态机」这个目标和「事件流」是有张力的：事件流要求客户端自己把事件应用成状态。折中方案是**事件携带它造成的补丁**，前端只做 `apply(patch)`，不写业务判断。

### 9.4 读秒与「长考」的交互

立直麻将里长考会消耗读秒，读秒用完才判超时。§9.1 定下来之前这条无法确定。

### 9.5 协议版本升级策略

`protocolVersion` 目前是整数，只定义了「不匹配就让用户刷新」。是否需要「服务端同时支持 v1 和 v2」的能力，取决于部署方式（单容器单实例的话不需要）。
