# 麻将算法验证指南

规则层写完（`internal/mahjong` 全部通过）之后，怎么确认它**真的是对的**？

这份文档回答这个问题。它同时覆盖 Go 测试的基础操作（如果你第一次写 Go）
和麻将算法特有的验证策略。

---

## 0. 先说结论

麻将算法不可能靠"跑一下看看输出对不对"来验证。真正能建立信心的是四类手段，
按性价比排序：

| 手段 | 抓什么错 | 需要知道正确答案吗 |
|---|---|:--:|
| **不变量** | 凭空造牌、丢牌、重复用牌、顺序依赖 | **不需要** |
| **构造法** | 漏判（该和的判成不和） | 不需要 |
| **穷举比对** | 误判（不该和的判成和） | 不需要 |
| **守恒律** | 算分错（谁付谁收、取整、本场棒） | 不需要 |
| **速查表** | 分错人、算错量 | 需要（但值是行业标准）|

前四类都不需要你预先知道答案——这是它们最值钱的地方。
**速查表是唯一必须依赖外部权威的部分**，好在点数就那么几张表，直接硬编码即可。

## 1. Go 测试基础（第一次写 Go 的话先看这节）

### 1.1 文件与命名规则

- 测试文件必须叫 `xxx_test.go`，和被测试的代码**放在同一个目录、同一个包**
- 测试函数必须叫 `TestXxx(t *testing.T)`，`Xxx` 首字母大写
- 同一目录下所有 `_test.go` 会被一起编译运行

```
internal/mahjong/
├── tile.go
├── tile_test.go        ← 测 tile.go
├── win.go
└── win_test.go         ← 测 win.go
```

### 1.2 常用命令

```bash
go test ./...                          # 跑全部包
go test ./internal/mahjong/            # 只跑规则层
go test -v ./internal/mahjong/         # 打印每个用例的通过情况
go test -run TestCanWin ./...          # 只跑名字匹配的测试
go test -run 'TestCanWin/七对子'        # 只跑某个子测试
go test -count=1 ./...                 # 禁用缓存，强制重跑
go test -cover ./...                   # 覆盖率
go test -race ./...                    # 竞态检测（房间层必跑）
```

> **`-count=1` 很重要**：Go 会缓存测试结果，输入没变就直接报 `cached` 不重跑。
> 改完代码看到 `(cached)` 别慌，加上 `-count=1`。

### 1.3 表驱动测试——Go 的标准写法

麻将算法有大量"同一函数、多组输入输出"的场景，表驱动是唯一合理的写法：

```go
func TestCanWin(t *testing.T) {
	tests := []struct {
		name string
		hand string
		want bool
	}{
		{"四顺子一雀头", "123m456m789m123s11p", true},
		{"七对子", "1133557799m1133p", true},
		{"国士无双", "19m19s19p1234567z", true},
		{"张数不足", "123m456m789m123s1p", false},
		{"凑不出雀头", "123m456m789m123s12p", false},
	}

	for _, tt := range tests {
		t.Run(tt.name, func(t *testing.T) {
			if got := CanWin(MustParseTiles(tt.hand)); got != tt.want {
				t.Errorf("CanWin(%q) = %v，期望 %v", tt.hand, got, tt.want)
			}
		})
	}
}
```

三个要点：

- **`t.Run` 让每个用例独立显示**，挂了能立刻看出是哪一个
- **失败信息里必须带上输入**。几十个用例，不写输入等于白跑
- 循环里用 `t.Errorf`（继续跑完其余用例）而不是 `t.Fatalf`（立刻中断）

### 1.4 辅助函数与 `t.Helper()`

测试里反复出现的断言应该抽成辅助函数：

```go
func mustTiles(t *testing.T, s string) []Tile {
	t.Helper() // 关键：让报错行号指向调用处，而不是这个函数内部
	tiles, err := ParseTiles(s)
	if err != nil {
		t.Fatalf("解析 %q 失败: %v", s, err)
	}
	return tiles
}
```

`t.Helper()` 不加的话，所有断言失败都会报在同一行，等于没有定位信息。

### 1.5 覆盖率怎么看

```bash
go test -coverprofile=cover.out ./internal/mahjong/
go tool cover -html=cover.out
```

会打开浏览器，**红色的是没执行到的行**。第一次看通常很有收获。

但请注意：**覆盖率只说明"执行到了"，不说明"结果对"**。
麻将算法的风险在于逻辑分支的**组合**，不在于漏写某一行。
覆盖率是及格线（本项目定在 90%），不是目标。

## 2. 不变量测试：不需要知道正确答案

这是麻将算法最有力的工具。核心思想：

> 与其断言「输出等于 X」，不如断言「输出必须满足某条性质」。

### 2.1 拆解的健全性（soundness）★ 最重要

`Decompose` 返回的**每一个**拆法，都必须通过这个校验：

```go
// validateDecomposition 校验一个拆法是否真的成立。
// 这个函数应该是整个测试代码里最严格的东西。
func validateDecomposition(t *testing.T, input []Tile, d Decomposition) {
	t.Helper()

	// 1. 面子数是 4（标准型）
	if len(d.Melds) != 4 {
		t.Fatalf("面子数 %d，期望 4", len(d.Melds))
	}

	// 2. 每个面子必须真的是顺子或刻子
	for _, m := range d.Melds {
		switch m.Kind {
		case MeldTriplet:
			if !(m.Tiles[0] == m.Tiles[1] && m.Tiles[1] == m.Tiles[2]) {
				t.Fatalf("刻子 %v 三张不一致", m.Tiles)
			}
		case MeldRun:
			a, b, c := m.Tiles[0], m.Tiles[1], m.Tiles[2]
			if a.Suit() != b.Suit() || b.Suit() != c.Suit() {
				t.Fatalf("顺子 %v 跨花色", m.Tiles)
			}
			if a.Rank()+1 != b.Rank() || b.Rank()+1 != c.Rank() {
				t.Fatalf("顺子 %v 点数不连续", m.Tiles)
			}
			if a.IsHonor() {
				t.Fatalf("顺子 %v 含字牌", m.Tiles)
			}
		}
	}

	// 3. 把雀头 + 全部面子的牌收集起来，多重集必须与输入完全一致
	var out []Tile
	out = append(out, d.Pair, d.Pair)
	for _, m := range d.Melds {
		out = append(out, m.Tiles[:]...)
	}
	if !sameMultiset(input, out) {
		t.Fatalf("拆解出的牌与输入不一致:\n输入 %s\n拆出 %s",
			FormatTiles(input), FormatTiles(out))
	}
}
```

**第 3 条一次性排除三类最隐蔽的 bug**：

| bug | 表现 |
|---|---|
| 凭空造牌 | 拆出来的牌比输入多 |
| 丢牌 | 拆出来的牌比输入少 |
| 重复用牌 | 同一张牌被算进两个面子 |

这三类靠肉眼看输出**几乎发现不了**（尤其在你的测试用例只有十几组的时候），
但一定会让符数和点数算错。所以这个校验函数要写得尽可能严格，
并且**在所有涉及拆解的测试里都调用它**——包括后面会讲到的穷举测试和模糊测试。

### 2.2 洗牌是排列

洗牌不能凭空多出牌，也不能弄丢牌：

```go
func TestShuffleIsPermutation(t *testing.T) {
	w := NewWallFromSeed(testSeed)
	if !sameMultiset(FullSet(), w.Tiles()) {
		t.Fatal("洗牌前后牌的多重集不同")
	}
}
```

### 2.2b 确定性 + 牌山指纹 ★ 牌山专属

前面说过「同一个种子必须产出同一副牌山」。但**只测"两次调用结果相同"是不够的**——
它在一个进程内成立，却挡不住"升级 Go 版本后行为变了"。

要把结果**固化成一个常量**：

```go
func TestWallFingerprint(t *testing.T) {
	w := NewWallFromSeed(testSeed) // testSeed 是写死的 [32]byte
	got := sha256.Sum256(w.Bytes())

	if got != wantFingerprint { // 常量也写死
		t.Fatalf("牌山指纹变了：\n得到 %x\n期望 %x\n"+
			"如果刚升级了 Go 版本，很可能是洗牌实现变了；"+
			"否则是你改动了洗牌算法，请确认后更新常量", got, wantFingerprint)
	}
}
```

**这条测试把"跨版本稳定"从一个假设，变成了一个会被发现的事实。**

它的失效场景很具体：Go 升级后，标准库 shuffle 的实现细节变了，
你的历史牌局全都验证不过了——而用户投诉之前，只有这条测试会告诉你。

**生成常量**：第一次跑的时候把实际值抄进 `wantFingerprint` 即可。
但**每次更新这个常量都必须说明原因**，否则它就从"护栏"退化成"橡皮图章"。

> ⚠️ 注意 `w.Bytes()` 而不是 `FormatTiles(w.Tiles())`。
> `FormatTiles` 按花色分组排序，**丢掉了摸牌顺序**——用它做哈希输入，
> 所有同花色组合的牌山会共用同一个指纹，验证彻底失效。
> 详见 [`docs/牌山可验证性.md`](牌山可验证性.md) 第 6 节。

### 2.2c 承诺与派生

牌山可验证性用到的纯函数也要测（都不需要网络或数据库）：

```go
// 同一输入必须得到同一承诺
// 改一个字节，承诺必须改变
// 交换两个玩家的 clientSeed，派生结果必须不同（顺序敏感）
// 改 gameID 或 roundIndex，派生结果必须不同（上下文绑定）
// 用记录里的种子重放，得到与存档逐张一致的牌山（端到端）
```

最后一条是**端到端验证**，它模拟的正是玩家自己核验的过程。

### 2.3 张数守恒

任何时刻，所有牌加起来必须是 136：

```
四家手牌 + 副露 + 牌河 + 牌山 + 岭上牌 = 136
```

这条不变量在**完整对局模拟**里特别有用（见第 6 节）。有两个时刻值得测：

```
发牌之后：      四家手牌各 13 张 + 牌山剩余 84 张 = 136
庄家摸第一张后：四家手牌 13+13+13+14 + 牌山剩余 83 张 = 136
```

**更该测的是"守恒"而不是具体数值**：四家手牌合计必须等于牌山减少的张数。
这条能抓住"发了 52 张、到手的只有 51 张"这类丢牌 bug——只断言某家有 13 张是抓不住的。

### 2.4 顺序无关性

把同一手牌**随机打乱顺序**，所有纯函数的结果必须完全一致：

```go
func TestOrderIndependence(t *testing.T) {
	hand := MustParseTiles("123m456m789m123s11p")
	want := Decompose(hand)

	for i := 0; i < 100; i++ {
		shuffled := shuffledCopy(hand, rand.New(rand.NewPCG(uint64(i), 0)))
		got := Decompose(shuffled)
		if len(got) != len(want) {
			t.Fatalf("打乱顺序后拆法数量变了: %d -> %d", len(want), len(got))
		}
		// 还可以进一步比对拆法集合（要注意拆法的表示顺序可能不同）
	}
}
```

**为什么这条重要**：算法里有大量"取第一张非零的牌"这类操作，
如果哪里漏了排序或引入了对输入顺序的依赖，这条测试会立刻炸。
而现实里玩家的手牌顺序是随机的，顺序依赖会导致"同样一手牌换个摸牌顺序就不和了"。

### 2.5 数值范围

有些输出的取值是有限的，越界即 bug：

```go
// 符数只可能是 {20, 25, 30, 40, ..., 110}
// 除 25（七对子）外，都是 10 的倍数
func validFu(fu int) bool {
	if fu == 25 { return true }
	return fu >= 20 && fu <= 110 && fu%10 == 0
}
```

翻数非负、役满倍数非负、点数必须是 100 的倍数——
这些都在随机测试里当作断言用。

## 3. 构造法：正向生成必然成立的输入

反向测试（拿一手牌问"能不能和"）有个根本缺陷：
**你无法确认"不和"的判定是漏了还是本来就该不和**。

正向构造给出**确定的**正例：

```go
// randomWinningHand 随机造 4 个面子 + 1 个雀头，结果必然是和牌型。
func randomWinningHand(r *rand.Rand) []Tile {
	var tiles []Tile
	for i := 0; i < 4; i++ {
		if r.IntN(2) == 0 {
			// 造顺子：随机花色 + 随机起点（点数 1-7）
			suit := Suit(r.IntN(3))
			start := r.IntN(7) + 1
			for k := 0; k < 3; k++ {
				tiles = append(tiles, MustTile(suit, start+k))
			}
		} else {
			// 造刻子：随机一种牌 ×3
			t := Tile(r.IntN(NumTileKinds))
			for k := 0; k < 3; k++ {
				tiles = append(tiles, t)
			}
		}
	}
	// 造雀头
	pair := Tile(r.IntN(NumTileKinds))
	tiles = append(tiles, pair, pair)
	return tiles
}
```

然后：

```go
func TestConstructedHandsAlwaysWin(t *testing.T) {
	r := rand.New(rand.NewPCG(42, 43))
	for i := 0; i < 100000; i++ {
		hand := randomWinningHand(r)

		// 注意：构造时可能让某种牌超过 4 张（比如造了两次「东东东」），
		// 那种手牌在现实里不存在，跳过
		if _, err := CountTiles(hand); err != nil {
			continue
		}

		if !CanWin(hand) {
			t.Fatalf("构造出的和牌型被判为不能和:\n%s", FormatTiles(hand))
		}
	}
}
```

**这一步能抓到"漏判"**：拆解算法的剪枝条件写窄了、回溯没走全、
某种面子组合没考虑到，都会在这里暴露。

反向也构造：

```go
// 造 13 张听牌 + 和的牌，断言 CanWinWith == true
```

### 构造法的进阶用法

刻意构造**边界情况**，而不是纯随机：

- 故意跨花色（顺子起点在第 7 张，如 `789m`）
- 故意用字牌（字牌刻子、字牌雀头）
- 故意制造**多种拆法**（如 `111222333m`）
- 故意贴近 4 张上限（同一张牌出现 4 次）

纯随机会很少命中这些边界，需要显式提高它们的权重。

## 4. 穷举比对：小规模域上的暴力验证 ★ 最能建立信心

这是全套方法里最有力的一招。

### 4.1 做法

写一个**又慢又笨但显然正确**的暴力实现，
在一个**小到能完全穷举**的域上，和你的优化实现逐一比对。

### 4.2 可行的域

全部 34 种牌的 14 张组合是天文数字，不可能穷举。但**限制在一种花色**就可以：

> 只含万子（9 种牌），每种最多 4 张，共 14 张。

这个域的大小是：

```
(1 + x + x² + x³ + x⁴)^9 展开后 x¹⁴ 的系数
= 118,800
```

**约 12 万个组合**，现代机器跑完只要几秒。完全可行。

### 4.3 暴力实现怎么写才算"独立"

关键是**不要抄优化版的思路**，换个角度看问题：

| | 优化实现 | 暴力实现 |
|---|---|---|
| 雀头 | 枚举计数 ≥2 的牌 | 同样枚举（这层没什么花样） |
| 面子 | 递归 + "取最小牌"剪枝 | **枚举所有可能的 4 个面子组合**，再看剩余是否成雀头 |
| 失效模式 | 剪枝条件写错 → 漏判 | 枚举不全 → 漏判 |

两者失效的位置不同，所以能互相暴露问题。

```go
// canWinBruteForce 用最朴素的方式判断：枚举所有面子的组合。
// 故意写得又慢又笨，只要保证"显然正确"。
func canWinBruteForce(tiles []Tile) bool {
	// 1. 先枚举所有可能的雀头
	// 2. 对每种雀头，枚举所有可能的 4 个面子组合
	//    （面子 = 所有合法顺子 + 所有合法刻子，直接穷举列表）
	// 3. 检查拼起来是否恰好用完所有牌
}

func TestExhaustiveSingleSuit(t *testing.T) {
	// 枚举所有「14 张、只含万子、每种不超过 4 张」的组合
	forEachMultiset(9, 14, 4, func(counts []int) {
		tiles := countsToTiles(counts, SuitMan)

		got := CanWin(tiles)
		want := canWinBruteForce(tiles)

		if got != want {
			t.Fatalf("实现不一致:\n%s\n优化实现=%v 暴力实现=%v",
				FormatTiles(tiles), got, want)
		}

		// 优化实现返回的每个拆法都要通过健全性校验
		for _, d := range Decompose(tiles) {
			validateDecomposition(t, tiles, d)
		}
	})
}
```

### 4.4 单花色域覆盖不到的地方

**单花色测试抓不到"顺子跨花色"的 bug**——因为域里根本没有第二种花色。

所以再补一个**跨边界的小域**：

> 只含 7p、8p、9p、1z、2z、3z 这 6 种牌，共 14 张
> （`C(6+14-1, 14) = 11,628` 个组合）

这个域的价值在于：

- `9p`(编码 26) 和 `1z`(编码 27) 在编码上**相邻**，正好横跨饼→字牌的边界
- 含字牌，能验证"字牌不能组顺子"
- 含 `789p`，能验证"顺子不能跨花色"

**12 万 + 1.2 万，两个域跑完不到一分钟。做完这一步，你对拆解算法的信心会远超任何手工用例。**

## 5. 模糊测试：Go 原生支持，专抓边界

Go 1.18 起内置模糊测试。

```go
func FuzzDecompose(f *testing.F) {
	// 种子：几个手写用例
	f.Add([]byte{0, 0, 0, 1, 2, 3})
	f.Add([]byte{})

	f.Fuzz(func(t *testing.T, data []byte) {
		tiles := bytesToTiles(data) // 任意字节 → 牌组

		// 不管输入多离谱，都不许 panic
		ds := Decompose(tiles)

		// 一旦返回了拆法，每个都必须合法
		for _, d := range ds {
			validateDecomposition(t, tiles, d)
		}

		// CanWin 与 Decompose 必须一致
		if (len(ds) > 0) != CanWin(tiles) {
			t.Fatalf("CanWin 与 Decompose 不一致: %s", FormatTiles(tiles))
		}
	})
}
```

```bash
go test -fuzz=FuzzDecompose -fuzztime=60s ./internal/mahjong/
```

模糊测试会自动变异输入去找 panic 和断言失败。

**注意**：fuzz 会生成**非法牌组**（张数不对、同种超过 4 张、空输入）。
你的函数必须优雅处理——返回空或错误，**绝不能 panic**。
这本身就是一条硬性要求：规则层是纯函数，输入不可信时也要稳。

## 6. 守恒律：验证算分的最强武器

点数是一个**零和游戏**。任何时刻，四家的分数总和必须恒等于初始总和。

```
初始 4 × 25000 = 100000
每一次和牌、流局、立直棒之后：sum(scores) == 100000
```

### 为什么这条这么强

它**不需要你知道正确答案**，但只要有任何"不守恒"就是 bug。能抓到的包括：

| bug | 守恒律的表现 |
|---|---|
| 支付矩阵写错（谁付谁收搞反） | 总和变了 |
| 取整方向错（四舍五入 vs 向上取整） | 总和变了 |
| 本场棒加算漏了或多加了 | 总和变了 |
| 立直棒没有正确转移 | 总和变了 |
| 自摸时算错了几家付款 | 总和变了 |

再配一条更细的：**和牌者的收入必须等于其他各家支出之和**。

### 怎么测

跑随机对局：

```go
func TestScoreConservationOverManyGames(t *testing.T) {
	r := rand.New(rand.NewPCG(7, 8))

	for game := 0; game < 10000; game++ {
		scores := [4]int{25000, 25000, 25000, 25000}

		// 随机造一个分数变动（一次和牌 + 本场棒 + 立直棒）
		payments := randomPayment(r)
		for _, p := range payments {
			scores[p.Seat] += p.Amount
		}

		// 校验
		sum := 0
		for _, s := range scores {
			sum += s
		}
		if sum != 100000 {
			t.Fatalf("第 %d 局点数不守恒: %v (总和 %d)", game, scores, sum)
		}

		// 收入 = 支出
		var income, expense int
		for _, p := range payments {
			if p.Amount > 0 { income += p.Amount } else { expense -= p.Amount }
		}
		if income != expense {
			t.Fatalf("收入 %d ≠ 支出 %d", income, expense)
		}
	}
}
```

如果房间层已经写完，更好的做法是**真的模拟完整对局**，
每一步之后都校验守恒——那样连房间层的状态转移错误也一并覆盖。

## 8. CLI 抽检：用来定位，不是用来验证

写一个小的命令行工具：

```bash
go run ./cmd/mahjongcalc -hand "123m456m789m11p123s" -win 1p -tsumo -dealer=false
```

输出：

```
和牌型：123m 456m 789m 123s + 11p
役种：  平和(1) 断幺九(1)
翻数：  2
符数：  30（副底20 + 门清荣和10）
点数：  子家荣和 2000
```

**它的用途不是验证，是调试。** 当有一个 failing test 时，
用它把中间结果打出来看，比在测试里到处加 `t.Logf` 快得多。

同时它也能用来和在线算点工具**人工对照**，抽检几十手。
注意：人工对照的覆盖率极低，只能作为辅助，**不能替代第 4 节的穷举**。

这个工具在验收演示时也用得上——能当场展示一手牌是怎么算出来的。

## 9. 回归快照

一旦对某批输入的结果有了信心，把它们固化下来：

```
internal/mahjong/testdata/scoring_golden.json
```

之后每次改动规则层，跑测试就会告诉你哪些结果变了。

> ⚠️ **golden file 最大的陷阱**：结果变了不代表错了，可能是你**改对了**。
> 所以每次快照变化都必须**逐条确认原因**，而不是无脑更新。
> 把它当成"提醒你这里的行为变了"，而不是"标准答案"。

Go 里读写 testdata 很方便，`testdata/` 目录会被 `go build` 忽略，
不会进二进制，是放测试数据的标准位置。
