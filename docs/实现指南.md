# 阶段一：规则层 `internal/mahjong`（任务书 §5）

这是整个项目最该先做、也最容易写出隐蔽 bug 的地方。**全程不需要数据库、不需要网络**，
跑 `go test ./internal/mahjong/` 就能得到反馈。

## 1.1 牌的类型（`tile.go`）

**产出**：牌的类型与编解码。

建议的接口形状：

```go
type Suit uint8
const ( SuitMan Suit = iota; SuitSou; SuitPin; SuitHonor )

type Tile uint8                       // 0..33

const ( NumTileKinds = 34; NumTiles = 136; HandSize = 13; WinningHandSize = 14 )

func NewTile(suit Suit, rank int) (Tile, error)
func MustTile(suit Suit, rank int) Tile
func (t Tile) Suit() Suit
func (t Tile) Rank() int
func (t Tile) IsNumber() bool
func (t Tile) IsHonor() bool
func (t Tile) Valid() bool
func (t Tile) String() string         // "一万" "东"
func FullSet() []Tile                 // 136 张
```

**关键决策**

- `Tile` 表示**种类**，不区分同类牌的四张副本。一副牌就是 136 个 `Tile` 值，
  重复出现即代表副本——**不要**设计成 `{Suit, Rank, CopyID}` 那样的结构。
- 字牌点数用命名常量（东=1 … 中=7），别在代码里散落魔法数字。
- 编码必须能被唯一还原：给定 `kind`，`NewTile(kind.Suit(), kind.Rank()) == kind`。

**常见坑**

- 顺子判断依赖编码的**连续性**：`0-8`、`9-17`、`18-26` 三段各自连续，
  这意味着 `i` 和 `i+1` 同花色当且仅当它们在同一段内。写顺子逻辑前先想清楚这点。
- 字牌点数越界（`8z`）必须是错误，不能静默截断。

**验收**

- [ ] 34 种牌逐个做「编码 → 花色+点数 → 重新编码」的往返测试，全部相等
- [ ] `FullSet()` 返回 136 张，且每种恰好 4 张
- [ ] 越界入参（万点数 0、万点数 10、字牌点数 8）都返回错误
- [ ] `IsNumber` 与 `IsHonor` 对全部 34 种牌互斥且完备

## 1.2 紧凑记法（`parse.go`）

**产出**：人类可读的牌组表示，测试用例、日志、数据库共用同一套。

```go
func ParseTiles(s string) ([]Tile, error)
func MustParseTiles(s string) []Tile
func FormatTiles(tiles []Tile) string
```

记法：`m`/`s`/`p`/`z` 表示万/条/饼/字牌，字母前的数字是点数。

```
"123m"              一万 二万 三万
"11z"               东 东
"123m456s789p11z"   共 11 张
```

**关键决策**

- 这是**测试可读性的基础设施**，先做它，后面所有测试用例都能一行写完手牌。
- `FormatTiles` 与 `ParseTiles` 必须互为逆运算，且 `FormatTiles` 输出稳定
  （建议固定按万→条→饼→字牌分组，便于断言）。
- 忽略空白字符，方便测试里排版。

**常见坑**

- 数字 `0` 不是合法点数，要报错而不是当成点数 0。
- 结尾挂着未指定花色的数字（`"123m4"`）要报错。
- 花色字母前没有数字（`"m"`）要报错。

**验收**

- [ ] `ParseTiles` → `FormatTiles` 往返对多组输入都相等
- [ ] 五种错误输入都返回错误（点数 0、结尾缺花色、花色前无点数、非法字符、字牌越界）
- [ ] 空字符串返回空切片且不报错

## 1.3 牌山（`wall.go`）

**产出**：洗牌、摸牌、发牌。

```go
type Wall struct { /* 私有字段 */ }

func NewWall(r *rand.Rand) *Wall      // r 为 nil 时用全局随机源
func (w *Wall) Remaining() int
func (w *Wall) Empty() bool
func (w *Wall) Draw() (Tile, bool)
func (w *Wall) Tiles() []Tile         // 完整摸牌顺序的副本
func (w *Wall) Deal() ([4][]Tile, error)
```

**关键决策**

- **随机源必须可注入**。`NewWall(r *rand.Rand)` 让测试能传固定种子，
  否则洗牌行为无法复现，`Deal` 的测试就只能靠"张数对"这种弱断言。
- `Draw` 返回 `(Tile, bool)` 而不是 panic：任务书规定「轮到玩家摸牌时牌山中无牌可摸」
  是一个**正常业务分支**（该小局流局结束），不是异常。
- `Tiles()` 返回**副本**。历史牌局要记录牌山，外部改动不能污染牌山状态。
- `Deal` 按任务书：庄家 14 张，三位闲家各 13 张。

**常见坑**

- `Tiles()` 直接返回内部切片是经典 bug——调用方一改，牌山就坏了。测试要覆盖这点。
- `Deal` 前必须校验余牌够不够（需要 13×3 + 14 = 53 张），不够要报错而不是少发。
- 发牌顺序要想清楚并写进注释，否则后面接对局逻辑时会含糊。

**验收**

- [ ] 新牌山 136 张，每种 4 张
- [ ] 相同种子两次洗牌结果完全一致；不同种子结果不同
- [ ] `Draw` 顺序与 `Tiles()` 返回的顺序一致
- [ ] 摸完 136 张后 `Empty()` 为真，再 `Draw` 返回 `ok=false`
- [ ] `Deal` 返回 13/13/13/14，牌山恰好消耗 53 张
- [ ] 余牌 52 张时 `Deal` 报错
- [ ] `Tiles()` 返回副本（改返回值不影响牌山）

## 1.4 手牌（`hand.go`）

**产出**：手牌的增删查。

```go
type Hand struct { /* 私有字段 */ }

func NewHand(tiles []Tile) *Hand      // 拷贝入参
func (h *Hand) Add(t Tile)
func (h *Hand) Remove(t Tile) error   // 失败返回可被 errors.Is 匹配的哨兵错误
func (h *Hand) Len() int
func (h *Hand) Count(t Tile) int
func (h *Hand) Tiles() []Tile         // 排序后的副本
func (h *Hand) Counts() Counts
func (h *Hand) CanWin() bool
func (h *Hand) Clone() *Hand
```

**关键决策**

- `Remove` **只删一张**。手上有三张一万，打出一张后还剩两张。
- `Remove` 失败时**不能改变手牌状态**，且错误要用哨兵值包装（`fmt.Errorf("%w: ...", Err)`），
  让上层能用 `errors.Is` 分类处理。
- `NewHand` 拷贝入参、`Tiles()` 返回副本、`Clone()` 深拷贝——三处都要做对，
  否则房间调度里会出现"改了一个快照结果原手牌也变了"的诡异 bug。

**验收**

- [ ] `NewHand` 拷贝入参（改源切片不影响手牌）
- [ ] 手上有 3 张时 `Remove` 一张后剩 2 张
- [ ] `Remove` 不存在的牌报错、可用 `errors.Is` 匹配、且手牌不变
- [ ] `Tiles()` 返回排序副本（改返回值不影响手牌）
- [ ] `Clone()` 与原手牌完全独立

## 1.5 和牌判定（`win.go`）★ 最难的一步

**产出**：给定牌组判断能否和牌。

```go
type Counts [NumTileKinds]int

func CountTiles(tiles []Tile) (Counts, error)   // 校验非法牌与「同种超过 4 张」

type MeldKind uint8
const ( MeldRun MeldKind = iota; MeldTriplet )

type Meld struct { Kind MeldKind; Tiles [3]Tile }
type WinningHand struct { Pair Tile; Melds []Meld }

func CanWin(tiles []Tile) bool
func CanWinWith(hand []Tile, t Tile) bool       // 自摸与荣和的共同入口
func Decompose(tiles []Tile) (WinningHand, bool)
```

### 规则边界（先想清楚再写）

任务书只认一种和牌牌型：**14 张拆成 4 个面子 + 1 个雀头**。

- 面子 = 顺子（3 张**同花色连续**数字牌）或刻子（3 张完全一样）
- 雀头 = 2 张完全一样
- **七对子、国士无双等形式一律不接受** —— 这是刻意的，不是漏实现
- **字牌不能组顺子**（东、南、西 不是顺子）
- **顺子不能跨花色**（八万、九万、一条 不是顺子）

### 算法思路

不要枚举所有排列组合，那是指数爆炸且容易写错。用这个观察：

1. 把 14 张转成 34 长度的计数数组。
2. **枚举雀头**：对每一种数量 ≥ 2 的牌，试着拿掉 2 张当雀头。
3. 剩下的 12 张必须能拆成 4 个面子。拆面子时有个关键性质：
   > 取**编号最小**的那张剩余的牌，在任何一个合法拆法里，它必然属于
   > ① 以它开头的顺子，或 ② 它自己的刻子。没有第三种可能。

   所以每一步只需尝试这两种归属，配合回溯即可，不需要遍历所有组合。
4. 任何一种雀头选法能让剩余全部拆完，就是和牌。

**顺子能否以编号 `i` 开头**：`i` 必须是数牌（`i < 27`）且 `i % 9 <= 6`
（点数不超过 7，否则 `i+2` 会越过 9 跑到下一种花色去）。这个条件建议单独写个小的
判定函数，它是整个判定里最容易写错的地方。

### 常见坑

- **回溯忘记恢复计数**。改了三张牌,分支失败后必须改回来，否则后续分支全被污染。
- **跨花色顺子**。`i % 9 <= 6` 这个约束漏掉的话，`789m` 会被判成能拆出 `89m1s`。
- **字牌被当成顺子**。字牌段内部编号也是连续的，光看 `i+1`、`i+2` 存在会误判。
- **`CountTiles` 不校验「同种超过 4 张」**。`11111m` 是非法牌组，
  虽然现实中不会出现，但作为纯函数的入参校验要挡住。
- **张数不是 14 时该怎么办**：`CanWin` 应当直接返回 false，而不是试图判定 13 张。

### 验收

准备一张表，至少覆盖这些正反例：

| 用例 | 期望 |
|---|---|
| `123m456m789m123s11p` | 和 |
| `111m234m567m789s22p` | 和（刻子+顺子混合）|
| `111m222m333m444s55p` | 和（四刻子）|
| `111z222z333z444z55z` | 和（字牌刻子）|
| `111222333m456s77p` | 和（同色多重拆法）|
| `123m456m789m123s1p` | 不和（只有 13 张）|
| `123m456m789m123s111p` | 不和（15 张）|
| `123m456m789m123s12p` | 不和（凑不出雀头）|
| `11m111s222s333s135p` | 不和（有雀头但余张不成面子）|
| `11223344556677z` | **不和**（七对子不接受）|
| `9m12s111p222p333p44z` | **不和**（顺子不跨花色）|
| `123z111m222m333m44p` | **不和**（字牌不组顺子）|
| `11111m234m567m899s` | 不和（同种超过 4 张）|

- [ ] 上表全部通过
- [ ] `Decompose` 返回的 `Melds` 恰好 4 个、`Pair` 正确
- [ ] `CanWinWith` 对 13 张手牌 + 1 张牌的判定正确
- [ ] `CanWinWith` **不修改**传入的手牌切片（这个很容易忘）

**验收**

## 2.2 `internal/auth`：密码与令牌

**产出**：bcrypt 哈希 + JWT 签发校验。

```go
func HashPassword(plain string) (string, error)
func VerifyPassword(hash, plain string) bool
func IssueToken(userID int64, secret []byte, ttl time.Duration) (string, error)
func ParseToken(token string, secret []byte) (int64, error)
```

**关键决策**

- **密码绝不明文**，也**绝不用 SHA/MD5**——必须 bcrypt（或 argon2），因为它自带加盐和慢哈希。
- JWT 用 HS256，secret 从环境变量读；**开发环境的默认 secret 不能进仓库**。
- **登出是个真问题**：JWT 是无状态的，服务端发出去就"忘"了。
  三个可选方案，按复杂度递增：
  1. 前端丢 token 了事（最简单，但 token 在过期前仍有效）
  2. 内存里的黑名单，带过期清理（单机够用，重启丢失）
  3. Redis 黑名单（多实例、可持久化）
  
  建议先做方案 2，在 README 或日志里说明取舍。

**常见坑**

- `ParseToken` 必须校验签名算法，防止 `alg: none` 攻击。
- token 过期时间是必填项，别用零值。

**验收**

- [ ] 同一个密码两次哈希结果不同（证明有盐），但都能校验通过
- [ ] 篡改过的 token 解析失败
- [ ] 过期 token 解析失败

## 2.3 `internal/user`：用例层

**产出**：注册、登入、登出三个用例。

```go
func (s *Service) Register(ctx context.Context, username, password string) (User, error)
func (s *Service) Login(ctx context.Context, username, password string) (string, error)
func (s *Service) Logout(ctx context.Context, token string) error
```

**关键决策**

- 用户名唯一性靠数据库的 **unique index**（`migrations` 里已经建了 `lower(username)` 的唯一索引），
  不要靠"先查再插"——那有竞态。
- 重名注册要把数据库的唯一约束错误翻译成**业务错误**，而不是把 SQL 错误透出去。
- 登入失败时，无论"用户不存在"还是"密码错误"，**对外返回同样的错误信息**，
  避免用户名枚举。

**验收**

- [ ] 重复用户名注册返回可识别的业务错误
- [ ] 密码错误与用户不存在的响应无法区分

## 2.4 `internal/api`：HTTP 接口

**产出**：路由 + 三个 handler + 鉴权中间件。

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/register` | 注册 |
| POST | `/api/login` | 登入，返回 token |
| POST | `/api/logout` | 登出（需鉴权）|
| GET | `/api/me` | 当前用户（需鉴权，用来验证中间件）|

**关键决策**

- **handler 要薄**：解析请求 → 校验 → 调用 `user.Service` → 编码响应。
  业务规则不许写在 handler 里。
- 错误码统一映射：业务错误 → 400，鉴权失败 → 401，未预期错误 → 500 且**不泄漏内部细节**。
- 中间件从 `Authorization: Bearer <token>` 取 token，解析后把 userID 放进 `context`。

**验收**（写成一个 `curl` 脚本，每次改完都能一键回归）

- [ ] 注册 → 登入 → 用 token 访问 `/api/me` 成功
- [ ] 不带 token 访问 `/api/me` 返回 401
- [ ] 重复注册返回 400 及明确信息
- [ ] 登出后原 token 失效

- [ ] 提交：`feat(auth): 实现用户注册、登入与登出`

# 阶段三：WebSocket 通信（任务书 §3）

## 3.1 协议设计

**先把协议定下来再写代码**，否则客户端和服务端会来回改。

建议统一信封：

```json
{ "type": "room.join", "data": { "roomId": "abc123" } }
{ "type": "error",     "data": { "code": "ROOM_NOT_FOUND", "message": "房间不存在" } }
```

**决策清单**

- 用 `type` 字符串路由，而不是数字枚举（调试时可读，日志友好）
- 客户端→服务端叫「指令」，服务端→客户端叫「事件」，命名成体系
- 每个消息类型定义明确的 Go 结构体，编解码集中在一处
- 版本号要不要？至少留个 `type` 前缀的位置（如 `v1.room.join`）

## 3.2 连接管理

**产出**：`internal/ws` 的连接生命周期。

用 `github.com/coder/websocket`。

**关键决策**

- **一个连接必须只有一条写路径**。WebSocket 并发写会破坏帧。
  标准做法是：读 goroutine 收消息投递到 channel，写 goroutine 从 channel 取并发送。
- 必须做**心跳**（ping/pong），否则连接断了服务端可能长时间不知道。
- 读要设 `SetReadLimit`，防止超大消息打爆内存。
- 连接关闭时要把该连接从所有注册表里摘干净，否则会向已关闭的连接发消息。

**常见坑**

- 在多个 goroutine 里直接写同一个连接 —— 必崩。
- 忘记处理写超时，一个慢客户端会卡住整个广播。
- 广播时对已关闭的 channel 发送 —— panic。关闭和注销要串行化。

## 3.3 调试客户端

任务书明确说："最好为接下来需要用到 WebSocket 功能的部分在编写服务端之余也编写一个
合理的客户端，便于你的调试以及验收时的讲解"。

**最低成本方案**：`web/` 下一个 HTML + 原生 JS，页面里能连、能发消息、能看到收到的消息。
让 Go 直接把它 serve 出来（避免跨域麻烦）。

**验收**

- [ ] 浏览器打开调试页，连上服务端
- [ ] 能收发 echo 消息

# 阶段四：房间与对局（任务书 §4、§5）

## 4.1 Hub：房间注册表

**产出**：房间的创建、查询、销毁。

**关键决策**

- Hub 自己也应该是一个 **actor**（单个 goroutine + channel），
  否则"创建房间"和"销毁房间"并发时会争用 map。
- 房间 ID 要好念（验收演示时要口头报出来），别用 UUID。

**验收**

- [ ] 创建房间返回 ID，能按 ID 查到
- [ ] 并发创建 100 个房间不出错（`go test -race` 通过）

## 4.2 Room：actor 模型

**产出**：房间状态机。

```go
type Room struct {
    commands chan command   // 外部只通过它投递指令
    // 以下字段只在 run() goroutine 内访问
    seats    [4]*player
    state    roomState
}
```

**关键决策（这是整个项目最重要的架构决定）**

- 每个房间一个 goroutine **独占**全部状态。外部**不直接读写**任何字段，
  只往 `commands` 投递指令。
- 好处：**不需要任何锁**。不存在忘记加锁、加锁顺序错误、死锁这些问题。
- 对外发消息通过**接口回调**，不直接依赖 WebSocket —— 这样房间逻辑能脱离网络测试。
  建议定义：

  ```go
  type Notifier interface {
      Send(userID int64, msg Message) error
  }
  ```

- 房间销毁要关闭 `commands`，并保证不会有人再往里发（关闭后的 channel 发送会 panic）。

**验收**

- [ ] 四个玩家加入后房间状态变为"可开局"
- [ ] 第五个玩家加入被拒绝
- [ ] `go test -race ./internal/room/` 通过（这是 actor 模型的核心验收项）

## 4.3 Game：对局推进

**产出**：四小局的完整流程。

任务书 §5 的流程，逐条对着实现：

1. **四小局**。第 N 小局的庄家是玩家 N（seat `N-1`）。
2. **每小局开始**：洗牌；庄家 14 张、闲家各 13 张；没有成为手牌的叫牌山。
3. **庄家先打一张**。
4. **之后从庄家下家开始循环**：摸一张 → 打一张 → 下家回合。
   下家顺序：玩家 1→2→3→4→1。
5. **小局结束条件**（两个之一）：
   - 有玩家和牌
   - 轮到某人摸牌时牌山已空 → 流局
6. **和牌判定**：
   - 摸牌后，手上 14 张能否构成和牌牌型 → **自摸**，其他三家付分
   - 别家打出一张后，自己 13 张 + 这张能否构成和牌牌型 → **荣和**，放铳者付分
7. **四小局结束后**按分数排序定顺位（一位~四位）。

**关键决策**

- 规则判定**全部**委托 `internal/mahjong`，`room` 里不许出现任何和牌逻辑。
- **分数规则自行发挥**（任务书原话），但要写进 README 或注释，别让它变成隐式约定。
  建议从简：比如自摸三家各付 1000，荣和放铳者付 3000，初始 25000。
- **每回合的动作要记录**，阶段五的历史牌局要靠它。建议在 `game.go` 里
  把「摸牌」「打牌」既推送给玩家，也追加到事件列表。
- 简化规则下**没有鸣牌**（吃/碰/杠），所以四家手牌始终是 13 张，
  和牌只在「摸牌后」或「别人打牌后」两个时机检查。这一点想清楚了代码会简单很多。

**验收**

- [ ] 写一个不依赖网络的测试：构造四个假玩家，跑完整场对局，断言流程合法
      （手牌张数守恒、牌山递减、每人摸打交替、最终有四人的顺位）
- [ ] 流局路径被覆盖（可以把牌山设小来强制触发）
- [ ] 自摸与荣和两条路径都被覆盖

- [ ] 提交：`feat(room): 实现房间 actor 与对局流程`

# 附录 A：易错点速查

这些都是我实际踩过或见过的高频坑：

| 坑 | 后果 | 正确做法 |
|---|---|---|
| `Tiles()` / `NewHand` 返回内部切片 | 调用方一改，源数据损坏 | 一律返回副本 |
| `while read` 读文件漏最后一行 | 校验清单静默漏检，还显示"全部通过" | `while read x \|\| [ -n "$x" ]` |
| `.gitignore` 里写 `x64/` | 匹配**任意层级**的 x64，误伤依赖目录 | 写 `/x64/` 锚定根目录 |
| WebSocket 多 goroutine 并发写 | 帧结构损坏 | 单写者 + channel |
| JWT 不校验签名算法 | `alg:none` 攻击 | 显式限定 HS256 |
| 回溯不恢复计数 | 后续分支全被污染 | 分支失败立即还原 |
| 顺子跨花色 | 错判和牌 | `i < 27 && i%9 <= 6` |
| 用户名唯一靠"先查再插" | 并发下有竞态 | 数据库唯一索引 + 错误翻译 |
| 写库阻塞房间 goroutine | 一个慢查询卡死整局 | 异步 worker |
