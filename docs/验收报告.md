## 五、任务书逐项验收

### §2 用户系统

**要求**：存储用户信息（ID、密码等）；注册、登入、登出。

**实现**

| 端点 | 方法 | 行为 | 关键状态码 |
| --- | --- | --- | --- |
| `/api/register` | POST | 注册 | 201 / 400 / 409 |
| `/api/login` | POST | 登入，签发 JWT | 200 / 400 / 401 |
| `/api/logout` | POST | 登出，令牌进吊销表 | 204 / 401 |
| `/api/me` | GET | 取当前用户 | 200 / 401 / 405 |

**关键设计决定（会被追问的三条）**

1. **密码用 bcrypt，不是自己造哈希。** bcrypt 自带盐与可调 cost，
   把"怎么存密码"这件容易做错的事交给被审计过的实现。
2. **登出需要服务端记一笔"已注销令牌"黑名单**（`auth.Revoker`），
   不是"删掉客户端的票"。JWT 是无状态的，服务端不存会话 ——
   所以"登出"必须由服务端记一笔吊销，否则票在过期前一直有效。
   （这一条是明明白白踩过才理解的，开发日志 10-12 有记。）
3. **分层错误翻译。** `store` 把 PostgreSQL 的 `23505` 翻译成 `store.ErrUsernameTaken`，
   `user` 再翻译成 `user.ErrUsernameTaken`，`api` 只认自己这层的词汇并映射 409。
   好处是 `api` **不 import `store`**，数据库细节不会漏到 HTTP 层——
   依赖方向是一条单向链，而不是一团。

**验收证据（2026-10-13 在本机实跑，服务端 + 真 PostgreSQL）**

```bash
$ bash scripts/serve.sh --bg
已启动，监听进程 PID=2368，端口 8080

$ curl -s -o /dev/null -w '%{http_code}\n' ...      # 逐项
注册成功                    201
重复用户名                  409
空用户名                    400
密码过短                    400
带多余字段（"admin":true）  400   ← 反序列化开了 DisallowUnknownFields
坏 JSON                     400
正确登入                    200
错密码登入                  401
无票取 /api/me              401
带票取 /api/me              200
GET 打 POST 端点            405

登出后再取 /api/me          401   ← 注销黑名单生效
```

13 项全中，含"带多余字段的注册请求被 400 拒掉"这条 ——
早期版本这里是 **201 静默接受**，是一个真实修掉的 bug。
`auth` 93.4%、`user` 91.3% 覆盖。

### §3 WebSocket 通信

**要求**：实现最基础的 WebSocket 连接测试；最好附一个客户端便于调试与验收讲解。

**实现（六步，每步都有可验收动作）**

| 步 | 内容 | 状态 |
| :-: | --- | :-: |
| 1 | 升级握手 + 立即回 `hello` | ✅ |
| 2 | 信封编解码 `{type, data}`，`data` 用 `json.RawMessage` | ✅ |
| 3 | 首帧鉴权 `auth` + 5 秒超时 + 认证前拒收 | ✅ |
| 4 | 连接管理：单一写路径、应用层心跳、读上限、连接注册表 | ✅ |
| 5 | `web/` 调试客户端，由 Go 直接 serve | ✅ |
| 6 | 决策回写协议文档 | ✅ |

**首帧鉴权而不是 `?token=`**：票放在 URL 会进服务端访问日志、浏览器历史、
反向代理日志；放首帧只在加密的帧里走。代价是连接多一个"连上了但还没认证"的状态，
**必须配超时**——否则谁都能开一堆空连接占着 goroutine 和 fd。

**四个关闭码**（验收现场按这个顺序演示最省事，调试页上一个按钮一个）：

| 码 | 怎么演 | 多快 |
| --- | --- | --- |
| `4401` | 连上不发 `auth` | 5 秒 |
| `4400` | 发一条非法 JSON | 立刻 |
| `4403` | 同一张票再开一条连接（顶号） | 立刻 |
| `4408` | 取消勾选「自动回 pong」 | 最长 20 秒（15s 间隔 + 5s 等待） |

**验收证据（对真 mux + 真 JWT 跑一次，`bin/ws-smoke.mjs`）**

```bash
$ node bin/ws-smoke.mjs
  ok   第一条是 hello   {"protocolVersion":1,"serverTime":...,"sessionId":"87a8f6bd..."}
  ok   hello.protocolVersion = 1
  ok   auth 后收到 authed   {"userId":26,"username":"smoke..."}
  ok   主动 ping 得到 pong + serverTime
  ok   #1 被顶号 → 4403   {"code":4403,"reason":"在别处登录","clean":true}
  ok   #2 仍然可用（pong）
  ok   非法 JSON → 4400   {"code":4400,"reason":"协议错误","clean":true}
  ok   不发 auth → 4401   {"code":4401,"reason":"认证超时","clean":true}
  ok   坏票先收到 error/AUTH_FAILED，随后 4401
全部通过
```

`4400` / `4401` / `4403` 三个码是在**真服务端**上实测到的；
`4408`（心跳超时）走的是单测路径，没在这次冒烟里等 20 秒 —— 演示时现场演它最直观。

**三个不能省的细节**（都是实测踩出来的，不是抄规范）

1. **一条连接只能有一条写路径。** 两个 goroutine 同时写同一个连接会让帧内容交错，
   对方解析出垃圾。规矩：**只有一个 goroutine 碰 `wsjson.Write`，别人的消息投 channel**。
   库的写锁保证不会崩，但**不保证顺序**。
2. **`SetReadLimit` 必须显式设。** 库默认 32768 字节，而一份逐座位定制的
   `game.snapshot` 很容易超过它，超了库**直接以 1009 关掉连接**。
   症状是"客户端隔一会儿莫名掉线"，本地测小消息永远不出现——典型的"上线才炸"。
3. **心跳用协议 §4.3 的应用层 `ping`/`pong`，不用库的传输层 `Ping`。**
   库的 `Ping` 超时那一刻会 `c.close()` **关掉整条连接**，于是"超时后再补发一条 4408
   关闭帧"物理上做不到。而且它绕过写 goroutine，等于第二个写者。

**客户端**：`web/` 由 Go 在 `GET /{$}` 上同源 serve，顺带免了 CORS；
**不能双击 HTML 打开**——`file://` 会发 `Origin: null`，被同源检查 403。
前端拆成状态机（`state.js`）、渲染（`render.js`）、连接（`wire.js`）、
指令（`cmd.js`）、牌面（`tiles.js`），牌面用 SVG，50 条前端用例全过。

### §4 游戏房间

**要求**：创建房间；玩家加入房间；人数满四人后可以开始游戏。

**实现**：Hub（房间注册表，本身也是 actor）、座位大厅、准备、开局条件、房主交接、
断线 120 秒保座、按座位裁剪的消息投影。

**房间号用 6 位可念字母表**（去掉 `0/O/1/I`，32 字符取模无偏置，如 `Y7KQ2P`）——
不是 UUID。理由很实际：**验收时要能口头报出来**。

**整个项目最重要的架构决定：actor 模型，不用锁。**

- 每个房间一个 goroutine **独占**全部状态，外部只往 `commands` 投指令，
  不存在"四个玩家并发操作同一局牌"的竞态。
- **好处不是"性能"，是"不需要论证正确性"**：没有锁就没有忘记加锁、
  加锁顺序错、以及"一次操作做到一半被插进来"这三类 bug。
- 也不给 `commands` 加关闭：往已关闭的 channel 发送会 panic。
  用 `stopped` + 一个 `closed` 原子标志判断"房间还在不在"。
- **那个 `closed` 原子标志不是多余的**：`run` 的 `select` 两支都就绪时是**随机挑**的，
  于是"刚销毁"和"还能投指令"之间有一个随机窗口，
  同一条指令有时成功有时报 `ErrClosed`。那种偶发最难查。

**掉线保座（协议 §4.5，2026-10-13 定）**：窗口 120 秒，期间随时重连回原座。
**窗口到了人没回来 → 关掉整个房间**，先 `room.seatVacated` 再 `room.closed{reason:"playerTimeout"}`。
**不释放座位让三家继续**：麻将少一个人打不了，而"中断/托管"那一套还没有。
做掉线续局时改这一处——那时该是**冻结对局等人回来**，不是把座位让给别人。

**验收证据**：19 条包内用例，覆盖创建/查找/并发创建 100 个房间/满座拒绝/
重连不占第二座/开局四道守卫/房主交接/断线超时/重连保座；
`-race` 通过；变异脚本 `bin/mutate-room.sh` 逐处改坏关键判断验证测试是否有牙。

### §5 游戏核心

**要求**：完整对局流程——洗牌发牌摸牌出牌、和牌与和牌判定、结束判断、分数制度。
任务书说"简化版即可"，**本项目按完整规则做**。

**规则层（`internal/mahjong`）—— 98.3% 覆盖率，纯函数、零 IO**

| 能力 | 说明 |
| --- | --- |
| 牌与记法 | 34 种牌编码 + 赤五独立维度；紧凑记法 `123m456s789p11z`，解析/格式化互逆 |
| 牌山 | 确定性洗牌、发牌、摸牌、**commit-reveal 可验证性** |
| 和牌型 | 标准型 / 七对子 / 国士无双；**枚举候选拆法**（拆法影响役与符） |
| 役种 | 全部役种的成立条件与门清/副露翻数 |
| 符数 / 算点 | 符数计算、基本点、满贯封顶、切上满贯、支付规则 |
| 宝牌 | 指示牌映射、表/里/赤计数 |
| 听牌 / 鸣牌 | `Waits` / `IsTenpai`；吃碰杠成立判定；立直成立判定 |
| 入口 | `Win` —— 把「和牌形 → 有役 → 非振听 → 役 → 宝牌 → 符 → 点数」串成一条 |

**赤宝牌为什么不做成"解析时归一成普通五"**：那样牌山指纹就**绑不住赤五的位置**，
服务器可以在公布承诺值之后再决定赤牌发给谁。赤属性做成叠加在种类之上的独立维度，
和牌判定/役种/符数只看种类，只有数赤宝牌时才区分。

**对局层（`internal/game`）—— 独立 actor**

规则层把线性循环变成**带等待的状态机**：简化版是"摸→打→摸→打"，
完整规则会被玩家的响应打断。这是本项目最难的一块，也是 actor 模型价值最大的地方：
**等待状态本身就是对局状态的一部分**，不需要额外的同步原语。

| 时机 | 触发 | 处理 |
| --- | --- | --- |
| 鸣牌询问 | 有人打出一张牌后 | 开窗口等其余三家回应 |
| 荣和 / 头跳 | 一张牌多家可荣和 | M-League 取头跳：放铳者下家 → 对家 → 上家，只认最近一家 |
| 自摸询问 | 自己摸牌后牌型可和 | 自己决定 |
| 杠 | 明杠 / 加杠 / 暗杠 | 摸岭上牌、翻新宝牌；加杠还要开抢杠窗口 |
| 回合超时 | 到点没打牌 | **自动打一张**，牌局不卡死 |

**已实现**：发牌、摸打、立直（宣言 / 锁手 / 一发 / 立直棒）、吃/碰/杠（明/加/暗）、
荣和窗口与头跳裁决、自摸与荣和结算、杠后岭上摸牌与新宝牌翻牌、
宝牌指示牌与赤牌计数、海底 / 河底、帕奥责任者、
荒牌流局与听牌料、连庄与本场、四人顺位与 M-League ポイント、每回合事件记录。

**已接通**（2026-10-13 晚，`5fa1653`）：`internal/ws` 的网关把协议 §5.2 / §5.3 的 13 条
指令分派到 `room` / `game` 的 actor 上，事件按座位回到各自的连接。四条真 WebSocket
连接打完整一场的用例在 `internal/ws/gateway_test.go`，真服务端的冒烟脚本是
`scripts/room-smoke.mjs`（见 §7.1）。**对局层到这一刻没有缺项了。**

规则判定**全部**委托 `internal/mahjong`——`room` / `game` 里不出现任何役种、
符数或点数计算。对局只负责"谁在什么时候可以做什么"。

**每个等待都必须有超时**（协议 §9.1：回合 5 秒 + 3×10 秒读秒，鸣牌窗 3 秒）：
一个掉线玩家能卡死整局，是这类项目最典型的线上事故。
注意 `deadlineMs` 只下发**基础**那一截，读秒在服务端只影响"何时裁定"——
把读秒也塞进去，前端就画不出读秒条。

**一处容易活到线上的算点错误**（写在代码注释里）：
M-League ポイント =（最终分 − **30000**）+ 顺位点 × 1000。
原点 30000 **不是**起始分 25000——写成后者会让每个人的ポイント整体偏高 5000，
而四个人之间的**相对**顺序看不出差别，所以错了也很难发现。

**验收证据**：14 条包内用例，覆盖开局隐藏他家手牌、摸牌只发给本人、
回合超时推进、荒牌流局、自摸与顺位、荣和窗口、碰优先于吃、
暗杠后岭上摸牌与新宝牌、海底自摸、河底荣和、帕奥责任者、立直宣言与锁手、快照按座位裁剪；
`game` 覆盖率 82.7%（当天刚加完杠、帕奥、立直与快照，测试还在追）。
变异脚本实测：**6 处变异 5 处被抓**，存活的那处（`canRon` 短路）如实记在 §7.4。

## 六、本项目的三个"独特之处"

答辩时抽一条展开就够，不要三条都讲。

### 1. 满覆盖的规则层 + 变异测试，而不是"写了测试"

规则层的每个常数都是**独立可错的事实**。测试用例数的判据不是"走没走同一个分支"，
而是"这一行是不是一个独立可错的正确答案"——
所以 §9 那张 11 行的点数速查表，虽然走同一个 `if`，**11 行全留**：
改错其中一个常数时，只有对应的那几行会挂。
（把这条判据搞反，会亲手删掉规则层最值钱的那些用例。）

### 2. actor 模型：把"并发正确性"变成"结构上不存在"

四个玩家同时操作一局牌，是这类项目最经典的一类 bug。
本项目没有用锁去解决它，而是让**状态只有一个 goroutine 能碰**。
于是"忘记加锁""加锁顺序错""读到半个状态"这三类问题不是"被测试覆盖了"，
而是**根本写不出来**。房间与对局各是一个 actor，之间只通过一个方向的回调来往。

### 3. 牌山可验证性：正面回答任务书的缘起

任务书的缘起是"小 X 认为平台在操控牌山"。所以本项目的牌山不是"洗了就发"，
而是 **commit-reveal**：开局先公布承诺值，赛后公布种子，任何人都能逐字节复算牌山。
契约写成了可复算的字节表，见 [`牌山可验证性.md`](牌山可验证性.md)。
**这是整个任务书里唯一直接回应"为什么要做这个项目"的那一页。**

## 八、常见追问速答

| 追问 | 答 |
| --- | --- |
| 为什么不用简化规则？ | 任务书 §5 的简化版只认 4 面子 + 1 雀头、不算番符。没有役就能和牌，那不是立直麻将。完整规则是 §7 的第一条加分项，我们直接当主线做了。 |
| 为什么自造牌山而不是用现成库？ | 牌山的**可验证性**是本项目的缘起（见 §6.3）。要 commit-reveal 就必须自己控制洗牌与承诺值，现成库不给这个契约。 |
| 为什么不用锁？ | 不是"锁不好"，是 actor 让**并发正确性变成结构性质**：状态只有一个 goroutine 碰，那三类锁 bug 写不出来。代价是每个 actor 一个 goroutine，且接口必须走 channel。 |
| 覆盖率多少？ | `mahjong` 98.3%、`room` 92.7%、`game` 82.7%、`auth` 93.4%、`ws` 91.5%。但更看重变异测试：覆盖率只说明"这行被执行过"。 |
| 覆盖率有别的口径怎么办？ | 有人跑出 `game` 88.5%、`README` 写规则层 99.1%——**同一快照上我实测的是 98.3%**。数字以复现命令的输出为准，不以文档为准；`game` 因为当天刚加完杠与帕奥，覆盖偏低。 |
| 测试里最花心思的是哪块？ | 算点。符数、满贯封顶、切上满贯、M-League 与通用日麻的差异，全是**独立可错的事实**，只能逐行对账。 |
| 最有信心的一处设计？ | 错误链的分层翻译：每层把错误翻译成**本层自己的词汇**，`api` 不 import `store`。它让数据库细节不可能漏进 HTTP 响应。 |
| 最大的技术风险在哪？ | 每个"等玩家响应"的时机都必须有超时。掉线玩家卡死整局是这类项目最典型的线上事故，所以鸣牌窗、回合、认证、心跳四处都有显式时限。 |
| **历史牌局怎么只做了一半？** | 见 §7.2。一句话：**数据层、用例层、HTTP 三块都完成且有测试，断在"谁来调用 `BeginGame`"这一步**——写路径的代码（有界队列 + 重试）写完了但没有调用方，没接在对局结束的回调上。这是**主动取舍**：剩下的接线要动 `room`/`game` 的回调，而那两块在冻结前仍在频繁改动，风险大于收益。 |
| 如果再多一周？ | 先接 §6 的写路径（**只差接线，代码都在**），再补同巡振听，然后补 `canRon` 那条缺失的用例。前两件是**已有代码的接线**，不是新功能。 |
| 最大的遗留问题是什么？ | 两条：**§6 历史牌局只到一半**（读路径能演、写路径没接线），和**同巡振听 / 立直后振听**没做（只有永久振听）。另外有一条测试缺口：`canRon` 改坏了没人喊（§4.4 的变异测试自己发现的）。 |

| 有没有用了 AI 辅助？ | 用了。但测试判据、规则出处、以及"这条测试删掉会漏掉什么缺陷"是逐条自己审的——§4.4 的变异测试就是为了让这件事可检查，而不是自述。 |
